## Why

This is the feature that makes the server a *library* rather than a file share: it discovers files on disk, turns them into books/series/library rows, and lets those groupings be curated. It is also where the guiding principle gets its first real test — directories currently come from the `BOOK_DIRS` env var, which can only be changed by restarting the process, so today the "changeable from both frontend and backend web view" rule is broken at the very first step. Completing the Tier 2 CRUD is what fulfils that principle for the core data model. Everything downstream (uploads, metadata enrichment, search, sensitive-content flags) operates on the rows this feature creates.

## Decisions

- **API-first, for everything.** Every mutation is an HTTP endpoint; the frontend and the backend admin UI are both just clients of the same API. Rationale (from the roadmap's guiding principle): it is the only way to actually *guarantee* that everything is changeable from both sides. If a behaviour lives only inside one UI, the principle is broken — so business logic stays in the backend, not in either UI.
- **Scannable directories move out of the env var and into a DB table.** Rationale: directories must be addable and removable at runtime from both UIs, which an env var cannot be. The code already carries the TODO for it ([api_caller.rs:2](../../src/routes/api_caller.rs#L2)). This is Tier 2 item #7.
- **Incremental scanning keys off the already-stored `file_hash` + `last_modified`.** Skip unchanged files rather than re-processing them. Both columns already exist and are populated by the scanner, so this is a read-and-compare change, not a schema change.
- **File watching builds on incremental scanning, not instead of it.** Filesystem notifications on file add/remove, debounced, then re-scan *only the modified folders*. The `notify` crate is the usual approach. Rationale for the ordering: a watch event is only useful if the re-scan it triggers can cheaply skip everything that didn't change.
- **Tier gating.** Finish every item in a tier before moving to the next; one thing in front of you at a time, no skipping ahead. So this section's CRUD work starts only after auth and 2FA (Tier 1) land — which is convenient, because the endpoints need an admin session to be gated on. The **[FE]** tasks below are the frontend track's F2 step ("Management": create/edit libraries & series, manage scannable directories), which only opens once this backend tier is done — a frontend screen can't precede the API it calls.
- **Series & library covers are user-definable, defaulting to the first entry's image.** Rationale: a scanned series has no cover of its own, so the sensible zero-config default is the first book's cover, with an explicit override available from both UIs.
- **Formats in scope: PDF / EPUB / CBZ / images.** The code commits to exactly this set — the extension allowlist is `pdf`/`epub`/`cbz`/`jpg`/`jpeg`/`png` ([folder_scanner.rs:281](../../src/scanner/folder_scanner.rs#L281)) and `BookFormat` has exactly `Pdf | Epub | Cbz | ImageComic | None` ([models.rs:83-89](../../src/data_models/models.rs#L83)). No CBR/CB7/MOBI/AZW3/DJVU.
- **A folder of page images is one book, not many.** `get_final_folder_path` stores the *parent directory* as `file_path` for `ImageComic` ([folder_scanner.rs:218-226](../../src/scanner/folder_scanner.rs#L218)), so the first image in a folder creates the row and the rest are skipped by the existing-path check. The cover is the first image in natural-sort order ([cover_image_retriever.rs:143-155](../../src/scanner/cover_image_retriever.rs#L143), via `natord::compare`).
- **Covers are content-addressed by the file's BLAKE3 hash.** `./cover_images/<hash>.<ext>` ([cover_image_retriever.rs:195-200](../../src/scanner/cover_image_retriever.rs#L195)). Identical files share one cover file, and re-extraction can be skipped with a simple `exists()` check.
- **Series identity is the lowercased parsed title.** `get_series_id` looks up by `title.to_lowercase()` and `create_series_entry` stores the lowercased name ([folder_scanner.rs:309](../../src/scanner/folder_scanner.rs#L309), [:322](../../src/scanner/folder_scanner.rs#L322)), while `books.title` keeps its original casing ([:139](../../src/scanner/folder_scanner.rs#L139)). Lowercasing is the de-facto dedupe key for "is this series already known".
- **One library is auto-created per scanned root, named after the directory and typed `Books`.** [folder_scanner.rs:360-368](../../src/scanner/folder_scanner.rs#L360). This is what the scanner does today, and it is why "create a library and assign specific series to it" is a genuinely new capability rather than a tweak.
- **The junction table stays a junction table.** `library_elements` has a composite PK and no `id` ([0001:32-38](../../migrations/0001_initial_schema.sql#L32)), so it deliberately does not implement `Extract`; series↔library links go through dedicated `Database` methods — insert via `Insert for SeriesLibraryConnection` ([insert.rs:130](../../src/database_related_scripts/insert.rs#L130)), delete via `remove_entry_from_library_elements` ([db.rs:304](../../src/database_related_scripts/db.rs#L304)), which is the sanctioned way past `remove_entry`'s junction guard ([db.rs:150-151](../../src/database_related_scripts/db.rs#L150)).

## Open questions

- **What request shape do `insert_entry` / `update_entry` take?** The stub says the shape is undecided. Options: (a) one generic envelope — `DatabaseTypes` + column/value pairs — which maps onto the existing `Update`/`ColumnSelector` machinery and needs only two endpoints; (b) per-resource typed endpoints (`POST /libraries`, `PATCH /libraries/{id}`, `POST /series`, …), which give real request validation and honest status codes at the cost of more handlers. **Suggested:** per-resource typed endpoints — the generic envelope pushes validation into the client and makes the API impossible to document.
- **RPC-style paths or resource paths?** The router's own comment block states the REST rule of thumb ([api_routes.rs:38-44](../../src/routes/api_routes.rs#L38)) but the paths are verbs: `/get_libraries`, `/delete_library/:id`, `/setup_db`, and `PUT /update_entry` alongside `PATCH /reading_progress/:id`. The `/api/v1` prefix was locked in early precisely so the frontend wouldn't couple to a shape we'd regret. **Suggested:** rename to resource paths now, while there is no client — the exact same argument that justified the version prefix.
- **What is `kind` in `GET /get_cover/:kind/:id`, and does it serve a file or a thumbnail?** No handler consumes it today. Options: `book | series | library` discriminating which table to look the path up in; or three separate routes. And separately: serve the stored full-size image, or a resized thumbnail for grid views. **Suggested:** `kind` = `book | series | library`, serving the stored file through `ServeFile` exactly as `request_file` does; keep thumbnail generation as the separate backlog idea rather than folding it in here.
- **Is a scan a request or a job?** `scan_all_directories` awaits inline and answers `"Directory scan complete"` ([api_caller.rs:307-315](../../src/routes/api_caller.rs#L307)) — but the reply is already untrue (unjoined tasks), and the existence of a `GET /scan/status` stub implies a job model. **Suggested:** spawn the scan, return `202` with a job id, and have `/scan/status` report progress; that also makes `POST /scan_directory/{id}` (scan one root) natural.
- **What happens to series and books when a library is deleted?** `library_elements` cascades but `books.series` has no FK, so today the rows are silently orphaned. Options: add the missing FK and cascade; or keep series alive and only unlink them (a series can legitimately belong to more than one library). **Suggested:** add the FK for integrity, but make library delete *unlink* rather than cascade-delete series — deleting a curated grouping should not delete content.
- **Does the scannable-directories table subsume `library`, or sit beside it?** Today directory and library are 1:1 (one auto-created library per `BOOK_DIRS` entry), but the roadmap wants curated libraries with hand-assigned series, which breaks that. **Suggested:** two separate tables — a scan root points at a *default* library for newly discovered series, and series can then be assigned to further libraries independently.
- **Where does `library_type` come from?** Auto-created libraries are hard-coded to `LibraryType::Books` ([folder_scanner.rs:363](../../src/scanner/folder_scanner.rs#L363)), yet the type is what routes metadata providers (§8) and what drives the upload dialog's default field set. **Suggested:** make `library_type` a required field on the create-library / add-scan-root endpoint, since nothing can infer it from the filesystem.

## Implementation notes

**Clear the two blockers first.** Nothing here is testable until (a) the five empty TOTP handler bodies at [api_caller.rs:617-625](../../src/routes/api_caller.rs#L617) return something so the crate compiles, and (b) the eight `:param` paths in [api_routes.rs:48-63](../../src/routes/api_routes.rs#L48) become `{param}` so the router stops panicking before `bind`. Both are mechanical.

**Crates.** `notify` must be added to [Cargo.toml](../../Cargo.toml) — it isn't there yet; `notify-debouncer-full` is the usual companion for the debounce the roadmap calls for. `walkdir` is already declared ([Cargo.toml:15](../../Cargo.toml#L15)) but unused, because the scanner hand-rolls the walk with `tokio::fs::read_dir`; either put walkdir to work inside `spawn_blocking` or drop the dependency. `futures` is also already declared ([Cargo.toml:10](../../Cargo.toml#L10)) and unused — see joining, below.

**Adding the directories table.** Follow the existing migration pattern: a new numbered `.sql` file plus a `Migration` entry in the `MIGRATIONS` array ([migrations.rs:16-20](../../src/database_related_scripts/migrations.rs#L16)); `include_str!` bakes the SQL into the binary, and each pending migration runs in its own transaction so the DB never half-migrates. (Your standing early-dev practice of editing `0001` in place and wiping the DB also works while there's no data to keep.) A new table then wants: a `DatabaseTypes` variant plus a `get_table_name` arm ([models.rs:18-39](../../src/data_models/models.rs#L18)), and one impl each of `FromRow` / `Extract` / `Insert` / `Update` / `Search`. Only `Insert` needs a hand-written query — `Extract` and `Update` just supply `TABLE`/`COLUMNS`/`Column` and inherit the SQL as default trait methods. **Name its primary key `id`:** `remove_entry_with_connection` hard-codes `WHERE id = ?1` ([db.rs:154](../../src/database_related_scripts/db.rs#L154)) and so do both `Update` methods, which is exactly why the auth tables keyed on `user_id`/`session_id` cannot be deleted or updated through those paths.

**Scan as a job — the Rust shape.** To answer before the work finishes you `tokio::spawn` the scan and keep progress in shared state, e.g. `Arc<Mutex<ScanStatus>>` (or `tokio::sync::RwLock` if reads dominate) that both the scan task and `/scan/status` hold a clone of. That means router state has to grow: it is `Arc<Database>` today ([api_routes.rs:21](../../src/routes/api_routes.rs#L21)), so you introduce an `AppState` struct holding the DB *and* the status handle (and, while you're there, the secrets that `main.rs` currently loads and drops), then change every handler's `State<Arc<Database>>` to `State<AppState>`. Do this once — it is a wide but shallow edit.

**Make "scan complete" true.** `scan_folder` spawns a task per file and drops the handle ([folder_scanner.rs:77-87](../../src/scanner/folder_scanner.rs#L77)). Collect the `JoinHandle`s into a `Vec` and `futures::future::join_all(handles).await` before returning. Note also [folder_scanner.rs:71-75](../../src/scanner/folder_scanner.rs#L71): `let permit = semaphore.acquire_owned().await.map_err(...)` produces a `Result` that is never `?`-ed, just moved into the task as `_permit`, so the concurrency limit isn't held the way it reads. And `create_book_entry`'s `Err` is thrown away — surface per-file failures into the scan status rather than swallowing them.

**Panic risk on the incremental path.** `BookMetadata::insert` does `convert_system_time_to_unix_time(self.last_modified.unwrap())` ([insert.rs:49](../../src/database_related_scripts/insert.rs#L49)); a file whose `modified()` is unavailable panics inside `spawn_blocking`. Incremental scanning is built on `last_modified`, so make it a real `Option` path when you touch it.

**Cover gotchas.**
- CBZ has no `final_path.exists()` short-circuit ([cover_image_retriever.rs:34-73](../../src/scanner/cover_image_retriever.rs#L34)), so every scan re-extracts and rewrites CBZ covers. PDF, EPUB and image folders do short-circuit ([:109](../../src/scanner/cover_image_retriever.rs#L109), [:135](../../src/scanner/cover_image_retriever.rs#L135), [:164](../../src/scanner/cover_image_retriever.rs#L164)). Add the same check to CBZ before you measure incremental scanning.
- `get_cover_output_path` builds the filename with `Path::with_extension` on the hash ([:198](../../src/scanner/cover_image_retriever.rs#L198)), and the caller passes `file_hash.clone().unwrap_or_default()` ([folder_scanner.rs:135](../../src/scanner/folder_scanner.rs#L135)) — so on a hashing failure the empty string joins to nothing and the extension lands on the *directory* name: the cover is written to `./cover_images.jpg`, a file beside the cover folder, shared by every such book. Guard on `Option<String>` rather than defaulting the hash.
- `COVER_DIR` is relative to the process working directory ([:13](../../src/scanner/cover_image_retriever.rs#L13)), which matters for packaging.
- The EPUB path is not just untested, it is probably picking the wrong image: it takes `epub.images.first()` ([:121-124](../../src/scanner/cover_image_retriever.rs#L121)), the first image resource, rather than the manifest/OPF `cover` item. The extension is derived as `media_type.split('/').nth(1)`, so `image/svg+xml` becomes an `.svg+xml` file.
- PDF covers need a resolvable dynamic pdfium library — the TODO at [cover_image_retriever.rs:75-76](../../src/scanner/cover_image_retriever.rs#L75) notes it should be bundled so macOS works without symlinking.
- CBZ picks the lexicographically smallest entry name ([:52](../../src/scanner/cover_image_retriever.rs#L52)) while image folders use natural sort (`natord`). Two different orderings for the same job — worth unifying on natural sort.

**Serving covers.** Reuse the streaming pattern: `ServeFile::new(path).oneshot(request)` ([stream_reader.rs:10-13](../../src/stream_reader.rs#L10)) gives range support and content-type detection for free, and returns a 404 response rather than an error for a missing file. Before serving, honour the TODO at [api_caller.rs:4](../../src/routes/api_caller.rs#L4) — check the path lies inside the scannable-directories table or `cover_images/`; see [Operations & Security](12-operations-and-security.md).

**Cover defaults.** "Default to the first entry's image" can be a *read-time* fallback (return the first book's `cover_image` when `series.cover_image` is NULL) or a *stored* value written at scan time. Decide once, deliberately: once a default is stored, you can no longer tell it apart from a value the user chose, so re-scanning can't safely update it. Related trap: `BookSeriesMetadata::from_row` wraps nullable columns as `Some(row.get(...)?)` ([db_from_row.rs:58-61](../../src/database_related_scripts/db_from_row.rs#L58)), so a NULL `cover_image` or `description` is a *type error*, not `None` — which will bite the moment covers are genuinely optional. `LibraryMetadata::from_row` does the same ([:73-74](../../src/database_related_scripts/db_from_row.rs#L73)).

**Series identity is fragile.** `get_series_id` treats a DB error exactly like "not found" and creates a new series ([folder_scanner.rs:312](../../src/scanner/folder_scanner.rs#L312)) — a transient failure silently duplicates a series. Fix before series become user-editable, or manual edits will fight the scanner. Also `get_id_from_table` carries the comment `//should not be used` ([db.rs:355](../../src/database_related_scripts/db.rs#L355)) yet the scanner is its only caller (three sites: [folder_scanner.rs:229](../../src/scanner/folder_scanner.rs#L229), [:306](../../src/scanner/folder_scanner.rs#L306), [:350](../../src/scanner/folder_scanner.rs#L350)); migrate them to `Database::search_for_single_row::<T>` when you're in there.

**Filename parser limits** (these constrain uploads too — the round-trip constraint in [Uploads & File Ingestion](05-uploads-and-ingestion.md) makes the naming convention a single shared spec between writing and reading): the single-letter aliases `v` / `c` / `p` match inside ordinary prose titles; only a space or `_` is allowed between keyword and digits, so `vol.3` and `v-3` don't match; brackets, parentheses and scanlator tags are not stripped; there is no decimal-chapter support, so `c01.5` parses as chapter 1.

**Format matching is case-sensitive** ([folder_scanner.rs:281](../../src/scanner/folder_scanner.rs#L281), [:286](../../src/scanner/folder_scanner.rs#L286)) — `.PDF` and `.JPG` files are silently skipped. Lowercase the extension before matching; `is_image_file` in the cover module already does this correctly ([cover_image_retriever.rs:173-180](../../src/scanner/cover_image_retriever.rs#L173)) and is the pattern to copy.

**Fix the library read before anything else in the CRUD group** — one word, `"name"` → `"library_name"` at [db_from_row.rs:71](../../src/database_related_scripts/db_from_row.rs#L71) — because every library endpoint, existing and planned, goes through it.
