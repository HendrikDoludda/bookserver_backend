# Browsing, Search & Discovery

> Full-text search across titles / authors / tags plus the browse-side furniture — an A–Z fast-scroll bar, filters, and sorting controls — that turns the raw list endpoints into something you can actually navigate.

**Status:** ⬜ not started · **Phase:** 1 · **Tier:** Backend Tier 3 (item #9 search); frontend F3 · **Tags:** [BE] [DB] [FE]
**Depends on:** [07 Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md) (the filter and sort controls need backend sorting + pagination) · [02 Reading & Read State](02-reading-and-read-state.md) (the completed / not-completed filter reads per-user read state)
**Blocks:** Nothing
**Roadmap:** [Build order](../../ROADMAP.md#priority-order-build-sequence)

## Why

Browsing works today only in the crudest sense: you can list libraries, list the series inside one, and list the books inside a series, in whatever order SQLite hands them back. With a real library that is unusable — you cannot find a title you half-remember, you cannot jump to the S's, and you cannot ask "what haven't I finished?". This section is what makes the catalog feel like a product rather than a database dump. The roadmap deliberately places it in Tier 3 ("makes it feel like a product") and calls search *mostly self-contained* — the `GET /search` route stub already exists, so the work is a handler and an index rather than new plumbing.

## Current state

Nothing of this feature is built. What exists is the ground it will be built on:

- **`GET /api/v1/search` is a route skeleton wired to the placeholder handler.** Registered at [api_routes.rs:65](../../src/routes/api_routes.rs#L65) pointing at `ping_server` ([api_caller.rs:239-241](../../src/routes/api_caller.rs#L239)), which returns `(StatusCode::OK, "pong")` and is documented in the code as *the* placeholder for functionality that doesn't exist yet.
- **No FTS5 anywhere.** A grep for `fts` / `FTS` / `MATCH` over `src/` and `migrations/` returns nothing. [migrations/0001_initial_schema.sql](../../migrations/0001_initial_schema.sql) is ten bare `CREATE TABLE IF NOT EXISTS` statements — **no virtual table and no indexes of any kind** on any table.
- **The browse endpoints are live but unordered, unpaginated and unfiltered.** `get_libraries` ([api_caller.rs:247](../../src/routes/api_caller.rs#L247)), `get_series_in_library` ([api_caller.rs:257](../../src/routes/api_caller.rs#L257)) and `get_series_children` ([api_caller.rs:268](../../src/routes/api_caller.rs#L268)) return `Json<Vec<WithId<T>>>` off bare id queries — `SELECT id FROM library` ([db.rs:280](../../src/database_related_scripts/db.rs#L280)), `SELECT series_id FROM library_elements WHERE library_id = ?1` ([db.rs:343](../../src/database_related_scripts/db.rs#L343)), `SELECT id FROM books WHERE series = ?1` ([db.rs:295](../../src/database_related_scripts/db.rs#L295)) — with no `ORDER BY` and no `LIMIT` anywhere in `src/`, and no auth: none of the three takes a session extractor, and the single `TODO: gate behind auth once sessions exist` sits over `get_libraries` ([api_caller.rs:246](../../src/routes/api_caller.rs#L246)).
- **The one generic read primitive is equality-only.** The `Search` trait ([db_search.rs:12-95](../../src/database_related_scripts/db_search.rs#L12)) builds `WHERE col = ?` predicates joined by `AND`/`OR` ([db_search.rs:26-30](../../src/database_related_scripts/db_search.rs#L26)) — no `LIKE`, no `MATCH`, no `ORDER BY`, and no `LIMIT` beyond the hardcoded `LIMIT 1` in `search_for_row` ([db_search.rs:40](../../src/database_related_scripts/db_search.rs#L40)). The three browse types are already wired into it — `BookMetadata`, `BookSeriesMetadata`, `LibraryMetadata` ([db_search.rs:97-110](../../src/database_related_scripts/db_search.rs#L97)) — so the types are ready but the SQL shape isn't.
- **`books.tags` is a comma-joined TEXT blob, not a relation.** Declared `tags TEXT` ([0001_initial_schema.sql:10](../../migrations/0001_initial_schema.sql#L10)), written as `self.tags.join(",")` ([insert.rs:42](../../src/database_related_scripts/insert.rs#L42)) and read back by splitting on `,` ([db_from_row.rs:27-31](../../src/database_related_scripts/db_from_row.rs#L27)). Both the FTS index and the tag filter have to work around that.
- **The fields search is supposed to cover are empty in practice.** The scanner hardcodes `author: "Unknown Author"` ([folder_scanner.rs:193](../../src/scanner/folder_scanner.rs#L193) and [:201](../../src/scanner/folder_scanner.rs#L201)) and `tags: vec![]` ([folder_scanner.rs:142](../../src/scanner/folder_scanner.rs#L142)), so author and tag search/filters have no real data until metadata enrichment or manual editing fills them.
- **Series names are stored lowercased** — `name: file_name.to_lowercase()` when the scanner creates a series ([folder_scanner.rs:322](../../src/scanner/folder_scanner.rs#L322)) — which makes A–Z bucketing case-insensitive for free but means display casing is currently wrong.
- **Read state does not exist** (no table, no column, no struct), so the completed / not-completed filter has nothing to filter on yet.

Roadmap drift: the status markers for §10 in [ROADMAP.md](../../ROADMAP.md) are all still correct (⬜ across the board), but the line "`GET /search` route stub already exists" overstates how ready that is — the route is registered yet unreachable, because `set_up_routes` uses axum 0.7 `:id` path syntax on eight routes ([api_routes.rs:48-63](../../src/routes/api_routes.rs#L48)) which axum 0.8 ([Cargo.toml:7](../../Cargo.toml#L7)) rejects with a startup panic, and the crate does not currently compile (5 errors, the empty-bodied TOTP handlers at [api_caller.rs:617-625](../../src/routes/api_caller.rs#L617)). Both are tracked in [Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md); neither is search work, but neither can be skipped before a search handler can be exercised.

## Decisions

- **Search engine: SQLite FTS5.** Search across titles / authors / tags uses SQLite's built-in full-text index rather than `LIKE` scans or an external search service. It stays inside the dependency we already have (`rusqlite`), needs no extra process, and gives ranking and tokenization for free.
- **Search is Tier 3 and "mostly self-contained".** It sits after auth (Tier 1) and core CRUD (Tier 2) in the build sequence, and is judged self-contained precisely because the route stub already exists and no other feature has to land first for the search box itself to work.
- **A–Z greying is computed client-side.** Letters/numbers with no matching series are greyed out and non-interactable, and the roadmap explicitly notes the greying is computable client-side from the series list — so this is **[FE]**-only, with no backend "which letters have entries" endpoint.
- **Sorting/pagination backend support lives in §6, not here.** The sort controls are the discovery-side surface; the backend list-endpoint support they sit on is tracked as its own Tier 3 item in [Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md), and the §10 filters depend on that same work.
- **The completed filter is read-state-derived.** "Completed / not-completed" comes from per-user read state (§2), not from a flag on `books` — so it is inherently per-user and inherits auth as a prerequisite.
- **Request input is never interpolated into SQL.** The codebase rule (values always bound via `?1` / `params!` / `params_from_iter`; table and column names only ever interpolated from trusted enums and consts) applies with full force here, since this is the first endpoint where free-text input drives a query *predicate* rather than being bound as a plain value.
- **Discovery ships as frontend F3.** Search, sort and filter land on the frontend together with "continue reading" and read/unread indicators, after backend Tier 3 — one coherent discovery pass rather than dribbled-out controls.

## Open questions

- **Is FTS5 actually available in the SQLite we link against?** `rusqlite` is declared with no feature list ([Cargo.toml:16](../../Cargo.toml#L16)) and `libsqlite3-sys` therefore resolves without the `bundled` feature ([Cargo.lock:1922-1928](../../Cargo.lock#L1922) — its only deps are `pkg-config` and `vcpkg`), so the binary links the *system* SQLite. FTS5 is present in this Mac's system SQLite — verified: `sqlite3 :memory:` (3.51.0) accepts `CREATE VIRTUAL TABLE t USING fts5(a)` and a `MATCH` query — but the Windows `.exe` / Docker targets in §11 packaging give no such guarantee. Options: enable `rusqlite = { features = ["bundled"] }` (ships a known-good SQLite with FTS5, at the cost of a C toolchain at build time and a bigger binary) · detect FTS5 at startup and fall back to `LIKE` (more code, two search behaviours to reason about). *Suggested:* turn on `bundled` in the same change as the FTS5 migration — it also removes a whole class of "works on my machine" packaging surprises.
- **How should tags be indexed and filtered, given the comma-joined column?** Options: index the raw comma string into FTS (free, but `sci` matches `sci-fi` and an *exact* tag filter becomes a delimiter-padded `LIKE`) · normalize into `tags` + `book_tags` tables (exact filtering and facet counts; `book_tags` would be a second `library_elements`-style junction with no `id`, so it would not implement `Extract` and would get dedicated `Database` methods) · both, with the junction as truth and FTS as the search index. *Suggested:* FTS over the existing blob for the search box first; normalize only when the tag *filter* needs exact matches and counts.
- **How does the index stay in sync?** Options: an external-content FTS5 table (`content='books'`) plus `INSERT`/`UPDATE`/`DELETE` triggers, so the scanner and every future write path stay untouched · repopulate the index at the end of each scan (simpler, but stale after any edit through `update_entry`). *Suggested:* external-content table with triggers — the write paths are about to multiply (uploads, metadata enrichment, manual edits) and each one would otherwise need remembering.
- **What does a search result look like?** A flat list of books · books grouped under their series · a mixed list of both series and book hits. Note that series names are lowercased at scan time, so any series hit will display in the wrong case until that's addressed. *Suggested:* return series and book hits in one response, each `WithId`-shaped and tagged with its entity type, so the frontend can render two sections from one round-trip.
- **A–Z greying vs pagination.** "Greying is computable client-side from the series list" holds only while the frontend has the *whole* list; once §6 pagination lands on the list endpoints, a paginated series list can no longer tell which letters are empty. Options: keep the series-per-library list unpaginated · add a cheap "distinct first letters" query for the bar. *Suggested:* leave the series list unpaginated (a home library's series count is small) and revisit only if one ever gets big.
- **"Recently added" has no column to sort on.** `books` carries `last_modified` (the file's mtime, [0001_initial_schema.sql:17](../../migrations/0001_initial_schema.sql#L17)) but no `created_at`. Options: sort by `id DESC` as a free proxy for insertion order · add a `created_at` column **[DB]** so the sort means what it says even after files are touched on disk. *Suggested:* `id DESC` now; add `created_at` when the §6 sorting work lands, since that's the change that has to define the sort keys anyway.
- **Should the author filter ship with the rest?** `books.author` is hardcoded to `"Unknown Author"` by the scanner, so the filter would offer exactly one value until metadata enrichment (§8) or manual editing fills it. *Suggested:* build the filter plumbing on the backend alongside search (it's nearly free once the query builder exists) but leave the author facet out of the UI until real values exist.
- **Does `/search` require a session?** The existing list handlers are still ungated (the standing `TODO: gate behind auth once sessions exist` at [api_caller.rs:246](../../src/routes/api_caller.rs#L246)), and Tier 3 comes after Tier 1, so a session extractor will exist by then; §9's possible "hidden from default views" protection for sensitive items also needs to know who's asking. *Suggested:* put `/search` behind the session extractor from the start and scope results to what the requesting user may see, rather than retrofitting it later.

## Done when

- [ ] `GET /api/v1/search?q=<term>` returns 200 with JSON hits that match on title, author **and** tag; a term with no matches returns an empty list, not an error.
- [ ] A search term containing FTS query syntax or quoting characters (`"`, `*`, `AND`, `-`) is treated as data: no SQL error, no 500, no leaked internal message.
- [ ] A book inserted or edited after the index was built appears in (or disappears from) search results without a manual reindex step.
- [ ] The series list screen renders the A–Z bar with letters that have no matching series greyed out and non-clickable; clicking a letter that has matches jumps to the first series starting with it.
- [ ] With read state in place, requesting `completed=false` returns only items the *current user* hasn't finished, and `tag=` / `author=` narrow the same list.
- [ ] A list request with a sort key (title / recently added / volume number) returns items in that order, and the order is stable across repeated requests.

## Implementation notes

- **FTS5 needs no crate.** It's a SQLite extension driven by ordinary SQL through `rusqlite`: `CREATE VIRTUAL TABLE books_fts USING fts5(title, author, tags, content='books', content_rowid='id')`, then `SELECT rowid FROM books_fts WHERE books_fts MATCH ?1 ORDER BY rank`. The catch is the one in Open questions — with no `bundled` feature the system SQLite decides whether FTS5 exists at all.
- **Bind the query, always.** `WHERE books_fts MATCH ?1` with the term as a parameter. Interpolating it would be both SQL injection and an FTS-syntax hazard, because FTS5's `MATCH` argument is its own little query language (`*`, `AND`, `NEAR`, quoting). Wrapping the user's phrase in double quotes before binding makes those characters literal. *Suggestion:* pick the tokenizer deliberately at `CREATE VIRTUAL TABLE` time (`porter` for stemming, or `unicode61 remove_diacritics 2`) — changing it later means rebuilding the index.
- **The `Search` trait will not carry this.** It only builds `col = ?` equality predicates. The Rust shape that fits the codebase is a new dedicated `Database` method next to `get_series_entries_in_library` ([db.rs:327-352](../../src/database_related_scripts/db.rs#L327)): a `&self` method that grabs a pooled connection and immediately delegates to an associated `*_with_connection(conn, …)` twin. That pairing is the house pattern and it's what lets the same query later run inside a `setup_new_transaction` closure.
- **Query parameters use Axum's `Query<T>` extractor** — a `#[derive(Deserialize)]` struct with `Option<…>` fields (`q`, `tag`, `author`, `completed`, `sort`, `limit`, `offset`) so every filter is optional. It works exactly like the `Json<T>` extractor already used in `sign_up` ([api_caller.rs:346-348](../../src/routes/api_caller.rs#L346)), just reading the query string instead of the body. Nothing in the codebase uses `Query` yet, so this is the first one.
- **Mixed result types** are cleanest as an `enum SearchHit { Series(WithId<BookSeriesMetadata>), Book(WithId<BookMetadata>) }` with `#[derive(Serialize)]` and, if the frontend wants a discriminator field, `#[serde(tag = "type")]`. `WithId<T>` already flattens the row id and the metadata into a single JSON object ([models.rs:10-14](../../src/data_models/models.rs#L10)), so each variant serializes as one flat object.
- **Suggestion — add plain indexes while you're in there.** With zero indexes on any table ([0001_initial_schema.sql](../../migrations/0001_initial_schema.sql) is ten bare `CREATE TABLE`s), filtering and sorting on `books.series`, `books.title` or `series.name` full-scans. A couple of `CREATE INDEX` statements are far cheaper than they look and matter more than FTS tuning for the browse screens.
- **Case handling:** series names are already lowercased at scan time, so A–Z bucketing is case-insensitive for free; for book titles (which keep their original casing) use `ORDER BY title COLLATE NOCASE` so `apple` and `Apple` sort together.
- **`books.tags` is delimited text**, so an "exact tag" filter over it means matching a padded string (e.g. comparing against `',' || tags || ','` and looking for `,tag,`) — correct only if the delimiters are normalized on write. That awkwardness is the strongest argument for the junction table in Open questions.
- **Warning kept from the roadmap:** greying the A–Z letters is *client-side* work computed from the series list. Don't build a backend endpoint for it.
- **Nothing here is reachable until the router starts.** The axum 0.8 `:id` → `{id}` path-syntax fix and the five TOTP compile errors both sit in front of any endpoint work; see [Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md).
