# Reading & Read State

> Serving book files to a reader client and remembering, per user, where they got to.

**Status:** 🟡 partial · **Phase:** 1 · **Tier:** Backend Tier 3 (item #8 per-user read state); frontend F1 for the readers, F3 for the read-state surfaces · **Tags:** [BE] [DB] [FE]
**Depends on:** [03 Authentication, Users & Sessions](03-auth-users-and-sessions.md) (read state is per-user, so it needs the session-derived user id) · [01 Library & Directory Management](01-library-and-directory-management.md) (there must be scanned books to read)
**Blocks:** [11 Browsing, Search & Discovery](11-browsing-search-and-discovery.md) (the completed / not-completed filter reads per-user read state) · [22 PDF Annotations](22-pdf-annotations.md) (shares the anchor/locator problem with read state)
**Roadmap:** [Build order](../../ROADMAP.md#priority-order-build-sequence)

## Why

Reading is the point of the whole server: everything else exists so a client can open a file and carry on where it left off. File serving with range support is already live, so the missing half is memory — per-user position, a finished flag, "continue reading", plan-to-read, and read/unread indicators. Read state is the first genuinely per-user feature, which is why it sits in Tier 3 — the tier that "makes it feel like a product" — behind auth (the Tier 1 dependency note names read state, uploads, sensitive content and the admin UI as all waiting on auth). Offline download and the per-format reader UIs are what turn a working stream into something a client can actually read from.

## Current state

- **Live:** [`streaming_file`](../../src/stream_reader.rs#L10) builds `ServeFile::new(&metadata.file_path)` and `oneshot`s the incoming request through it, so HTTP range and conditional handling come free from `tower-http`. The `.unwrap()` at [stream_reader.rs:12](../../src/stream_reader.rs#L12) is safe: `ServeFile`'s error type is `Infallible`, and a missing file yields a 404 response rather than an `Err`.

No auth, and no check that the served path is inside a configured book dir (file-header TODO at [api_caller.rs:4](../../src/routes/api_caller.rs#L4)). Its own comments at [api_caller.rs:284-285](../../src/routes/api_caller.rs#L284) note it should also handle images (cover images), partial books and folders of images (an unzipped CBZ), and that image comics "probably need to have their height pre-calculated in order for correct display conditions".

Missing ids already map to 404 via [error_types.rs:77](../../src/error_types.rs#L77).

## Decisions

- **Range streaming via `tower-http`'s `ServeFile`, not a hand-rolled reader.** [stream_reader.rs](../../src/stream_reader.rs) delegates the whole request to `ServeFile`, which handles `Range`, `Content-Range` and conditional headers for us. Rationale: it is correct HTTP for free and it is what the Phase 2 video plan explicitly wants to reuse — "direct-play file streaming with range support (like `stream_reader` does for books)". The stale `StreamReaderErrors` enum is the fossil of the abandoned alternative.
- **Serving is by row id, never by client-supplied path.** `GET /book/{id}` looks the path up from the database. Rationale (from §11 Operations & security): path-traversal protection is therefore not urgent today — "safe today since serving is by id; becomes real with uploads §4".
- **Read state is per-user, so it is gated on auth.** Tier 3 item 8 is "Per-user read state + 'continue reading' (§2) — needs auth", and the Tier 1 note names read state as one of the things waiting on the auth keystone. No point building it before §3 lands.
- **Read state stores a position *and* a finished flag** — the §2 task wording is "current page/locator + finished flag". Two distinct pieces of information: a position that resumes reading, and a boolean that drives the checkmark and the completed/not-completed filter. A position alone can't say "I finished this".
- **Offline download is a separate capability from streaming.** §2 lists it as "let the app download a file for offline reading (distinct from streaming)" — the reader streaming ranges and the app taking a whole copy for later are different jobs, even if they read the same bytes.
- **Reader UI is per format, not one reader.** "PDF, EPUB, and CBZ/image readers differ" — three implementations on the frontend, which is also why the reading *position* can't be one shape (see Open questions).
- **`user_id` comes from the session token, never from the request body.** Carried over from the §11 application-level auth-hardening list: "the single rule that prevents acting as another user; get it right when the `AuthUser` extractor (§3) lands". Every read-state endpoint here is bound by it — a book id in the path, a user id from the extractor.
- **Every read-state mutation is an HTTP endpoint.** From the guiding principle: both the frontend and the backend admin view are clients of the same API, so progress must not live only inside the reader client.

## Open questions

- **Format-aware reading position — what shape does the position column take?** (Ideas list #4: "'page number' works for PDF/CBZ, but EPUB needs a locator/CFI (reflowable text has no fixed pages). Worth designing the read-state schema with this difference in mind from the start.") Options: (a) one nullable `page` INTEGER plus one nullable `locator` TEXT, so each format uses the column that fits — readable, but every reader has to know which to look at; (b) a single opaque `position TEXT` the client writes and reads back, with the backend never interpreting it — simplest schema, but then the backend can't compute "page 40 of 200" progress for a badge; (c) `position TEXT` plus a separate normalized `progress_percent` REAL that the client also supplies, so the backend can sort and display without parsing. *Suggested:* (c) — opaque position for correctness across formats, plus a percentage the backend can order "continue reading" by and render progress from without ever parsing a CFI.
- **Is "finished" set explicitly, or derived from reaching the last page?** Options: a manual mark-as-finished only (predictable, but readers forget); auto-set when the position hits the last page/end-of-book (convenient, but wrong for a book someone flicks to the end of); both, with the auto-set only on a real end-of-content event from the reader. *Suggested:* both — reader reports end-of-content, and the API also accepts an explicit toggle so a user can mark or un-mark anything.
- **How are unread counts computed for series/library badges?** Options: an aggregate query per list request (a grouped `LEFT JOIN` from `books` to read state, one query for the whole list — fits the "Batched list queries (no N+1)" discipline §6 already marks ✅); or denormalized counters kept on `series`/`library` (fast reads, but a second source of truth to keep correct on every progress write and every scan). *Suggested:* the aggregate query — the library is small enough, and a counter that drifts is worse than a join.
- **Does `/reading_progress/{id}` carry the "continue reading" list too, or does that need its own endpoint?** The existing skeleton is a single path with `PATCH` and `GET` keyed by `:id`, which reads as one book's state. Continue-reading is a *list* scoped to the calling user, with no id. Note the router's own comment block at [api_routes.rs:37-44](../../src/routes/api_routes.rs#L37) already flags that the current paths are RPC-style verbs rather than resource paths. *Suggested:* keep `GET|PATCH /reading_progress/{book_id}` for one book and add a separate collection endpoint for continue-reading, so the list can grow sorting/pagination (§6) without overloading the item route.
- **Offline download: separate endpoint, or the same one with a flag?** Options: a distinct `GET /book/{id}/download` that adds `Content-Disposition: attachment` (explicit, easy to auth and log separately); a query parameter on `GET /book/{id}` (fewer routes, but muddies the streaming path); or nothing server-side at all, letting the client just read the whole range (no way to distinguish a download from a read in logs or rate limits). *Suggested:* a distinct download route — the roadmap already treats download as distinct from streaming, so the API should say so too.
- **Should `retrieve_metadata` be generalized before or after read state?** Its own comment wants it to serve every metadata type, and a reader opening a book will likely want series context in the same trip. *Suggested:* leave it book-only for now; revisit when the reader UI shows what it actually needs.

## Done when

- [ ] A request with `Range: bytes=0-1023` to `GET /api/v1/book/{id}` returns `206 Partial Content` with a `Content-Range` header and exactly 1024 bytes.
- [ ] `GET /api/v1/book_metadata/{id}` for an id that isn't in `books` returns 404 with no internal detail in the body; a valid id returns the book's JSON.
- [ ] `PATCH /api/v1/reading_progress/{book_id}` with a valid session stores the position against *that session's* user and the matching `GET` returns it — a page number for a PDF/CBZ, a locator the EPUB reader resumes from without a page number; two users reading the same book keep independent positions, and a request with no valid session gets 401.
- [ ] The continue-reading surface lists only the calling user's books that are started and not finished, most recently read first, and a book marked finished drops out of it.
- [ ] A finished book shows its checkmark and its series' unread-count badge drops by one, computed from a single query rather than one query per book.
- [ ] A downloaded file opens in the reader with the network off.

## Implementation notes

- **Nothing here can be exercised until the crate compiles and the router stops panicking.** Fix the five empty TOTP handler bodies ([Two-Factor Authentication (TOTP)](04-two-factor-auth-totp.md)) and change every `:id` path segment to `{id}` for axum 0.8 ([Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md)) first. `set_up_routes()` is called from `start_server` at [api_routes.rs:21](../../src/routes/api_routes.rs#L21), before `TcpListener::bind`, so the panic aborts the process before the port opens.
- **Read state is a junction-shaped table.** Its natural key is `(user_id, book_id)` — composite PK, no `id` column — which puts it in the same bucket as `library_elements`: it should *not* implement `Extract`, whose default methods hard-code `WHERE id = ?1` and read `row.get(0)` as the row id ([extract.rs:19-69](../../src/database_related_scripts/extract.rs#L19)). Give it `FromRow` + `Insert` + `Search` and dedicated `Database` methods (fetch-by-user, fetch-for-book, upsert-one) instead. The same caveat applies to the `Update` trait, whose SQL is `UPDATE {TABLE} SET {col} = ?1 WHERE id = ?2` ([db_update.rs:16-32](../../src/database_related_scripts/db_update.rs#L16)) — it already misfires on `sessions` (`session_id`), `recovery_codes` (`recovery_id`) and the `user_id`-keyed tables, so don't add another victim.
- **Upsert shape in Rust:** because `Insert` has no default method and each impl hand-writes its own SQL ([insert.rs:10-12](../../src/database_related_scripts/insert.rs#L10)), progress-saving can be a single `INSERT INTO read_state (...) VALUES (...) ON CONFLICT(user_id, book_id) DO UPDATE SET position = excluded.position, ...` — one statement, no read-then-write race, and it fits the existing trait as-is.
- **Handler shape:** an authenticated handler takes its extractors in order and the body last — `async fn set_progress(session: AuthSession, State(db): State<Arc<Database>>, Path(book_id): Path<i64>, Json(body): Json<ProgressUpdate>)`. Axum only lets the *final* argument consume the body, and the request DTO needs `#[derive(Deserialize)]` — several existing DTOs get this wrong (bare structs taken by value, `State` after the body), which is why those handlers can't be registered; the structs in [totp_model.rs](../../src/data_models/totp_model.rs) have no `Deserialize` at all.
- **Don't overload `books.page_number` or `books.page_count`** for read position. `page_number` is filename-parsed by the scanner; `page_count` is always NULL. A per-user position has no business on a shared `books` row anyway — and note that "page 40 of 200" progress needs a real `page_count`, which nothing produces yet.
- **Timestamps:** the codebase stores times as unix seconds via [`convert_system_time_to_unix_time`](../../src/database_related_scripts/db.rs#L412) and reads them with [`convert_to_system_time`](../../src/database_related_scripts/db_from_row.rs#L172), which **errors on NULL** rather than yielding `None`. If read state gets a nullable `last_read_at`, read it as `Option<i64>` directly rather than through that helper.
- **Serve image-comic pages, not the folder.** Because `file_path` is the parent directory for `ImageComic` ([folder_scanner.rs:218](../../src/scanner/folder_scanner.rs#L218)), the reader needs either a per-page route (book id + page index → the natural-sorted file inside that folder, the same `natord` ordering the cover picker uses at [cover_image_retriever.rs:143-171](../../src/scanner/cover_image_retriever.rs#L143)) or a stored page list. The pre-calculated-height note in [api_caller.rs:285](../../src/routes/api_caller.rs#L285) belongs to this same problem.
- **Offline download:** the simplest form reuses `ServeFile` and adds `Content-Disposition: attachment; filename="..."` to the response (either set it on the returned `Response` in the handler, or layer `tower_http::set_header` on just that route). `tower-http` is already pulled with `features = ["full"]` ([Cargo.toml:40](../../Cargo.toml#L40)) even though only `services::ServeFile` is used today.
- **Sorting and pagination for the continue-reading list are §6 work** ([Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md)); build the endpoint so it can take them later rather than returning an unbounded list forever.
- **Consider deleting `StreamReaderErrors`** rather than carrying six variants nothing constructs — same reasoning the roadmap applies to the unused signing key ("if nothing consumes it, remove it rather than carry unused crypto").
- **No tests exist anywhere in the repo.** Read state is a good first candidate for the §6 testing plan: the upsert and the "two users, one book" case are small, pure DB-layer assertions.
