# Internationalization (i18n)

> A backend-owned translation catalog, served over the API, so users can pick a display language and adding a new language is pure data entry instead of a code change.

**Status:** ⬜ not started · **Phase:** 1 · **Tier:** Frontend track F0 — build right after Backend Tier 1 and before F1 · **Tags:** [BE] [DB] [FE]
**Depends on:** [03 Authentication, Users & Sessions](03-auth-users-and-sessions.md) (the per-user language preference is part of per-user settings)
**Blocks:** [06 Backend Admin Web View](06-admin-web-view.md) (its text must go through t("key") from the first screen, against the same backend-owned catalog) · [14 Email & Notifications](14-email-and-notifications.md) (only for localized bodies; the catalog makes the emails translate for free)
**Roadmap:** [Build order](../../ROADMAP.md#priority-order-build-sequence)

## Why

Goal: users pick a display language, and **adding a new language never forces a rework**. The architecture is a day-one decision because retrofitting i18n into a frontend full of hardcoded strings is exactly the "complete rework" this project is trying to avoid — the same lesson as putting the `/api/v1` prefix in before the frontend couples to it. Because the catalog is *data in the backend* rather than bundled locale files, it also satisfies the project's guiding principle (everything changeable from both the frontend and the backend web view) and the notification **emails localize for free** ([Email & Notifications](14-email-and-notifications.md)) — the backend already has both the catalog and the user's locale, so no separate email catalog is needed.

## Decisions

- **Architecture (DECIDED): backend-owned catalog, served over the API.** One catalog lives in the backend as the single source of truth; both frontends (main app + the admin UI of [Backend Admin Web View](06-admin-web-view.md)) fetch strings via an API call rather than bundling their own locale files. Rationale: it fits "changeable from both sides", and since it is data in the backend, translations can be edited from the admin UI and the notification emails from [Uploads & File Ingestion](05-uploads-and-ingestion.md) / [Email & Notifications](14-email-and-notifications.md) localize for free — the backend already has the catalog *and* the user's locale, so no separate email catalog is needed.
- **The admin UI uses the same catalog (resolved).** The admin UI fetches from the **same backend-owned catalog** as the main app — one source of truth, no separate locale files. Both clients just call the i18n API.
- **Key ownership (DECIDED): code owns keys, admins own values.** A "line" (key) exists because the frontend calls `t("namespace.key")`, so keys live in version control next to that code; developers add a line when they add UI text. The **admin panel adds *languages* and fills in *values*** — it does not invent or delete keys, so the catalog can never drift out of sync with what the code actually references. Adding a language is therefore pure data entry, never a code change or a hand-written JSON file (which was the original goal).
- **Admin management (DECIDED): the admin UI edits the catalog directly.** Its layout mirrors the data model: pick/add a **language** (display name + **icon**, enabled flag, default flag, sort order); **tabs = namespaces**; each tab lists its **keys as input boxes**. An untranslated box shows the default-language (English) text as placeholder for context, and the same `LEFT JOIN` that powers that placeholder gives a free "N/M translated" progress view per language. Every save bumps the catalog version.
- **Three tables (DECIDED), fitting the existing conventions.** `locales` (the languages an admin manages), `translation_keys` (the canonical, code-owned key list = the tabs + lines), and `translations` (the filled-in values). `translations` is a **junction table** — composite PK `(locale_code, key_id)`, **no `id`** — so like `library_elements` it does *not* implement `Extract`; it gets dedicated `Database` methods (fetch-by-locale, upsert-one) instead.
- **Catalog is keyed by key, never by the English string**, per locale, grouped into namespaces/sections (e.g. `common`, `settings`, `library`, `options`, `reader`).
- **English base is a developer artifact.** Keys + English text are seeded from the repo (a seeder or, during early dev, the initial migration); every other language is pure DB data added and edited only through the admin UI.
- **Retrieval strategy (DECIDED): fetch once, cache, re-check by version.** The default is to fetch the whole catalog for the chosen locale once, cache it locally, and re-check periodically (e.g. daily, or on app start) via the version/ETag — so normal use is a local lookup with no per-screen round-trips. **Section-scoped retrieval is the fallback**, for the rare case where a screen needs strings that are not yet cached.
- **Fallback locale, in two places.** A missing key falls back to the default (English) so a half-translated language still works; and in the admin editor, a field that is **emptied falls back to the English entry on save**, so there are never empty boxes in the application.
- **Language icon lives on `locales`.** Start simple — an emoji flag, or a short id the frontend maps to a bundled icon; optionally later reuse the `cover_images` upload path for custom art.
- **Timing (DECIDED): start the *structure* at F1, not the translations.** ⚠️ Retrofitting i18n into a frontend full of hardcoded strings is exactly the "complete rework" to avoid. So wrap UI text in `t("key")` from the first screen even while only English exists; adding languages then becomes catalog edits. The *architecture* is a day-one decision; the *translations* are low-priority polish for whenever. (Same lesson as the `/api/v1` prefix.)
- **Scope: UI chrome only.** This system translates **UI chrome** ("Continue reading"). Library/series names and descriptions are **user data**, not UI text, so they are not translated by it.
- **Sequencing: F0, backend-only, small.** Build this catalog + `GET /i18n/:locale` (+ section scoping + version/ETag) right after backend Tier 1 and *before* F1, so the frontend can wire `t("key")` against a *real* endpoint from its first screen.

## Open questions

- **Route prefix and Axum path syntax for the endpoint.** The roadmap writes the endpoint as `GET /i18n/:locale`, but the cross-cutting-polish decision already nests every API route under `/api/v1` ([api_routes.rs:69](../../src/routes/api_routes.rs#L69)), and the pinned `axum = "0.8.9"` ([Cargo.toml:7](../../Cargo.toml#L7)) rejects the 0.7 `:param` form outright — the eight route paths that still use it ([api_routes.rs:48](../../src/routes/api_routes.rs#L48) onward, one of them `/get_cover/:kind/:id`) panic at router construction on 0.8. *Suggested:* register it as `/api/v1/i18n/{locale}` and treat `/i18n/:locale` in the roadmap as shorthand, not a literal path.
- **Is the catalog endpoint authenticated?** The per-user preference decision says an unauthenticated client falls back to browser/OS locale, which implies the login screen needs strings before anyone is signed in. Options: leave `GET /i18n/...` open (simple, and it is only UI chrome — no user data) vs. gate it behind a session (consistent with everything else, but then the login screen can only ever show bundled English). *Suggested:* leave the read endpoint unauthenticated and make only the catalog *writes* admin-only.
- **Where does the per-user locale actually live?** The roadmap says "stored on the user (ties into §3 per-user settings)", but §3's per-user settings table does not exist and `users` has no column. Options: a `language` column on `users` (one migration, trivially joinable at login) vs. waiting for the per-user settings table (avoids a second migration later). *Suggested:* whichever §3 lands first; if a settings table arrives, put it there — and remember `UserMetadata::insert` ([insert.rs:109](../../src/database_related_scripts/insert.rs#L109)) only writes three columns today, so a new `users` column must be added to that `INSERT` or it will never persist.
- **How are plural forms represented in a flat key → value catalog?** Options: one key per CLDR plural category (`library.unread.one`, `library.unread.other`) — keeps the backend a dumb string store and lets the frontend library pick the category; or store an ICU MessageFormat string as the single value — fewer keys, but the admin now types syntax into a text box and can break it. *Suggested:* separate keys per plural category, since keys are code-owned anyway and admins should only ever type prose.
- **Is the catalog version global or per-locale?** A single counter is simpler, but a German edit would then invalidate every English client's cache. *Suggested:* per-locale version/ETag, since the admin edits one language at a time.
- **Which locale do sign-up-time emails use?** Emails localize "for free" from the user's stored locale, but the verification email is sent during sign-up, before that user has ever picked a language. Options: default locale, the `Accept-Language` header, or a locale field in the sign-up request. *Suggested:* accept a locale in the sign-up body and store it on the user immediately, so even the first email is localized.

## Tasks

### Backend catalog (F0 — before the first frontend screen)

- ⬜ **Data model — three tables**, fitting the existing conventions **[DB]**:
  - `locales` — the languages an admin manages: `code` (BCP-47, e.g. `de`, `pt-BR`), `display_name`, `icon`, `is_default`, `enabled`, `sort_order`.
  - `translation_keys` — the canonical, code-owned key list = the tabs + lines: `namespace`, `key`, optional `description` (translator hint); `UNIQUE (namespace, key)`.
  - `translations` — the filled-in values: `(locale_code, key_id) → value`. A **junction table** (composite PK, **no `id`**), so like `library_elements` it does *not* implement `Extract`; it gets dedicated `Database` methods (fetch-by-locale, upsert-one) instead.
- ⬜ Catalog is keyed by **key** (never by English string), per locale, grouped into **namespaces/sections** (e.g. `common`, `settings`, `library`, `options`, `reader`) **[BE]**
- ⬜ **English base (keys + English text) is a developer artifact** seeded from the repo (a seeder or, during early dev, the initial migration); every other language is pure DB data added/edited only through the admin UI **[BE][DB]**
- ⬜ **Language icon** stored on `locales` — start simple (an emoji flag, or a short id the frontend maps to a bundled icon); optionally later reuse the `cover_images` upload path for custom art **[BE][FE]**
- ⬜ `GET /i18n/:locale` endpoint returning that locale's strings **[BE]**
- ⬜ **Section-scoped retrieval** — a screen can request just the namespaces it needs in the chosen language in one call (e.g. `GET /i18n/:locale?sections=settings,library,options`), instead of pulling unrelated strings **[BE]**

### Frontend wiring (from F1's first screen)

- ⬜ A `t("some.key")` lookup used everywhere instead of literal UI text **[FE]**
- ⬜ **Pluralization + interpolation** handled (`"{count} unread"`; plural rules differ per language) — the two classic i18n gotchas **[FE]**

### Behaviour & preferences

- ⬜ **Fallback locale** — a missing key falls back to the default (English), so a half-translated language still works. The fields when emptied will fall back to the english entry on save so there will be no empty boxes in the application. **[BE][FE]**
- ⬜ **Per-user language preference** stored on the user (ties into §3 "Per-user settings"); fall back to browser/OS locale, then default, when not logged in **[DB][BE][FE]**

### Must-haves for the served-catalog approach (the cost of not bundling files)

- ⬜ **Client-side cache + bundled fallback** — the app needs strings before first paint and must work offline (§2 offline reading). Cache the fetched catalog locally and ship at least the default language baked in, so a cold/offline start still renders **[FE]**
- ⬜ **Versioned fetch (ETag / version number)** so clients only re-download when the catalog changed, not on every load **[BE][FE]**
- ⬜ **Runtime-loadable lookup** — most i18n libs expect files at *build* time; serving at runtime means loading JSON into a map + lookup (or a package that supports remote loading, esp. on Flutter) **[FE]**

## Done when

- [ ] `GET /api/v1/i18n/en` returns every seeded key grouped by namespace, and the response is built from the catalog tables rather than any hardcoded string in Rust.
- [ ] `GET /api/v1/i18n/de?sections=settings,library` returns only those two namespaces, and none of the others.
- [ ] A locale with only some values filled returns the English text for every missing key, so no client ever receives an empty string.
- [ ] Saving an emptied input box in the admin catalog editor stores the English text for that key, and re-fetching that locale shows the English text rather than a blank.
- [ ] A repeat request carrying the previous version/ETag gets `304 Not Modified`; after any catalog save the same request gets a fresh `200`.
- [ ] The first frontend screen renders with zero literal UI strings — every visible label comes from `t("key")` — while only English exists in the catalog, and a verification email sent to a `de` user arrives in German from that same catalog.

## Implementation notes

- **No new backend crate is needed.** `serde_json` is already declared and unused ([Cargo.toml:14](../../Cargo.toml#L14)); the response can be a `HashMap<String, HashMap<String, String>>` (namespace → key → value) handed to `axum::Json`, which serializes it as nested JSON objects.
- **The `translations` Rust shape:** because the table has no `id`, do *not* implement `Extract` or `Update` for it — `Extract::extract` hardcodes `WHERE id = ?1` ([extract.rs:21](../../src/database_related_scripts/extract.rs#L21)) and `Update::update` hardcodes `WHERE id = ?2` ([db_update.rs:23](../../src/database_related_scripts/db_update.rs#L23)). Copy the `library_elements` pattern exactly: an `Insert` impl for the row struct ([insert.rs:130](../../src/database_related_scripts/insert.rs#L130)) plus dedicated `Database` methods next to [db.rs:304](../../src/database_related_scripts/db.rs#L304) / [db.rs:327](../../src/database_related_scripts/db.rs#L327). Follow the house convention of a `&self` method that grabs a pooled connection and a paired associated `*_with_connection` function taking `&Connection`, so the same logic can run inside `setup_new_transaction` ([db.rs:388](../../src/database_related_scripts/db.rs#L388)).
- **The fetch-by-locale query is a `LEFT JOIN`**, and it does double duty: `translation_keys LEFT JOIN translations ON key_id AND locale_code = ?` gives you the value or `NULL` per key. `COALESCE(value, english_value)` in that one query implements the fallback locale, and `COUNT(value)` over the same join is the "N/M translated" progress figure the admin UI wants — one query, three features.
- **Upsert-one is `INSERT ... ON CONFLICT(locale_code, key_id) DO UPDATE SET value = ?`** — SQLite supports this, and it is the right shape for "admin types in one box and saves" without a read-then-write round trip.
- **The `sections` query parameter is request input, so it must not be interpolated into SQL.** The project's SQL-safety rule is that only trusted enums/consts ever reach a `format!`-ed query. Bind the requested namespaces as parameters in a generated `?1..?n` IN-list — exactly what `Extract::extract_batch` already does for id lists ([extract.rs:33](../../src/database_related_scripts/extract.rs#L33)) — or validate each name against the known namespace list first.
- **Route syntax:** on `axum = "0.8.9"` the capture must be written `{locale}`, not `:locale`; the eight route paths still on the old 0.7 `:param` form ([api_routes.rs:48](../../src/routes/api_routes.rs#L48) onward) panic at router construction, so expect to fix those before any new route is reachable. The crate also does not currently compile — five empty-bodied TOTP handlers at [api_caller.rs:617](../../src/routes/api_caller.rs#L617) return `()` where `Response<Body>` is declared — so F0 lands on top of that fix.
- **ETag handling is manual.** Nothing in the stack does it for you: read `If-None-Match` from the request headers, compare against the stored catalog version for that locale, and return `StatusCode::NOT_MODIFIED` with no body when they match. Bump the stored version inside the same transaction as every catalog write, so a save can never leave clients caching stale strings.
- **Seeding the English base:** register a new numbered `.sql` in the `MIGRATIONS` array ([migrations.rs:16](../../src/database_related_scripts/migrations.rs#L16)) — never edit an already-applied migration. During early dev the standing practice is to edit `0001_initial_schema.sql` in place and wipe the DB, which is fine for the seed while no real data exists; once the frontend depends on the catalog, the English base wants its own seeder so re-seeding does not require a wipe.
- **Localizing the emails is a substitution, not a rewrite:** the two `format!` bodies at [auth.rs:176](../../src/routes/auth.rs#L176) and [auth.rs:363](../../src/routes/auth.rs#L363) become catalog lookups with interpolation, which is what the TODO at [auth.rs:171](../../src/routes/auth.rs#L171) is waiting for. Note that interpolation then has to work backend-side too, not only in the frontend `t()` — a small `replace("{name}", …)`-style helper is enough; there is no need for a full ICU implementation in Rust.
- **Do not confuse the two "language" concepts.** `BookLanguage` ([models.rs:115](../../src/data_models/models.rs#L115)) is content metadata about a book; `locales` is UI chrome. Nothing should map one onto the other.
- ⚠️ **The one warning worth repeating:** the structure comes first, the translations come whenever. A frontend built with literal strings and "we'll add i18n later" is the failure mode this whole section exists to prevent.
