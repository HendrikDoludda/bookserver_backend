# Cross-Cutting Backend Polish

> The small, high-leverage backend chores that don't belong to any one feature but block several: request-body parsing, honest HTTP status codes, list sorting/pagination, the `/api/v1` prefix, batched queries, clean startup wiring, and a testing strategy.

**Status:** 🟡 partial · **Phase:** 1 · **Tier:** Backend Tier 0 (all three items — landed in the code, but see Current state: the roadmap now marks the tier 🟡 rather than ✅) plus Backend Tier 3 item #10 for sorting + pagination; the testing strategy is unscheduled · **Tags:** [BE]
**Depends on:** Nothing
**Blocks:** [01 Library & Directory Management](01-library-and-directory-management.md) (the crate must compile and the router must bind before any scan or CRUD route works) · [03 Authentication, Users & Sessions](03-auth-users-and-sessions.md) (the crate does not compile and the router panics at startup; both block every auth route) · [11 Browsing, Search & Discovery](11-browsing-search-and-discovery.md) (the filter and sort controls need backend sorting + pagination)
**Roadmap:** [Build order](../../ROADMAP.md#priority-order-build-sequence)

## Why

Most of the roadmap is blocked behind a few foundational pieces, and three of them were tiny: a derive, a router `nest`, and a `match` arm in one `IntoResponse`. Doing them first meant the rest of the ladder never had to wait on a one-line change, and the `/api/v1` prefix in particular is trivial now and painful once a frontend has coupled to the unprefixed paths. The remaining two items are different in character: sorting + pagination is the backend half of the §10 browsing UI, and the testing strategy is new territory that will make every later change safer to make.

## Decisions

- **Tier 0 goes first, and it is deliberately tiny.** Each of the three items is a one-to-few-line change with outsized leverage: the derive unblocks the stubbed write handlers, which unblock create/edit in §1; the prefix has to precede any client; the status code is a `match` arm. The gating rule applies here as everywhere — finish every item in a tier before the next, one thing in front of you at a time, no skipping ahead.
- **`/api/v1` prefix before the frontend couples to it.** Trivial now, painful later: once a frontend has hard-coded unprefixed paths, moving them is a coordinated change across two codebases. `/health` stays at the root because liveness checks are infrastructure, not API surface. The roadmap treats this as the canonical example of a day-one architecture decision — the i18n timing note explicitly cites it ("Same lesson as the `/api/v1` prefix").
- **`Deserialize` on every model, one derive per struct.** The models already had `Serialize` for the read path; adding `Deserialize` makes the same struct usable as a `Json<T>` request body, so write endpoints don't need a parallel set of DTOs.
- **`EntryNotFound` → 404; 5xx details logged server-side, generic body to the client.** A missing row is a client-addressable condition, not a server fault, and a 500 for it makes the API impossible to consume correctly. The paired half of the decision is that when it *is* a server fault, the detail goes to the log and only a status plus a generic message goes over the wire — internal error text can leak implementation detail.
- **Batched list queries, never N+1.** The list handlers fetch ids first, then one `IN`-list query for the rows, so a library with 500 series is two queries rather than 501. `WithId<T>` exists for exactly this: the metadata structs don't carry their own id, so the batch path pairs the row id with the struct and flattens it in JSON.
- **Typed errors at the boundary, `anyhow` only at the top.** `start_server` returns `RoutingErrors` with the underlying `std::io::Error` as `#[source]`; `main` is the one place that widens to `anyhow::Result` and attaches human context.
- **Sorting + pagination lives in Tier 3, not Tier 0.** It's backend support that the §10 filters and sorting controls depend on, so it's scheduled with the discovery work rather than with the un-blockers. §10 names the sort fields the backend has to support — title, recently added, volume number, etc. — and the filters that ride on the same queries: completed / not-completed, by tag, by author.
- **Testing is new territory — plan to learn Rust testing together, walking through the first few.** The scope is deliberately narrow to start: unit-test the DB layer (extract / insert / batch) and validate the EPUB cover path, which has never been exercised.

## Open questions

- **Does the `/api/v1` item stay ✅ while the router still panics at startup?** The nesting is genuinely in place, so the *decision* has landed; the eight `:id` paths are an axum 0.7→0.8 migration bug, not a missing feature. Options: (a) call the item done and track the path-syntax fix wherever routing bugs live, (b) reopen it to 🟡 until a request actually reaches a nested route. *Suggested:* fix the eight paths as part of this section (it is a mechanical `:id` → `{id}` change across one file) and keep the marker ✅ afterwards — a done marker on an API prefix that no request can traverse is misleading.
- **Is `RequestErrors::RequestFailed` a 400 or a 500?** The mapping says 400, three call-site comments say 500, and the variant currently covers both "the request was malformed / the cookie layer isn't installed" and "the database lookup blew up". Options: (a) keep it 400 and delete the misleading comments and the dead 5xx branch, (b) split it into a client-fault variant (400) and a server-fault variant (500) and keep the branch. *Suggested:* (b) — the two conditions genuinely need different statuses, and a real 500 path is what makes the `is_server_error()` logging branch worth having.
- **How far does "generic error bodies" extend?** The decision is recorded against `DatabaseError` here, and §11's hardening list ([12-operations-and-security.md](12-operations-and-security.md)) carries it as its own item for the auth handlers. Right now the auth handlers do the opposite. Options: (a) give `AppErrors` an `IntoResponse` so handlers can `?` instead of hand-building responses, (b) keep hand-building but strip the interpolated `err.to_string()`. *Suggested:* (a) — it removes `create_internal_server_error_response` entirely and makes the sanitising behaviour the default rather than something each handler has to remember.
- **Offset/limit or cursor pagination, and what may be sorted?** Options: offset/limit is trivial to implement and matches an A–Z fast-scroll / page-number UI; cursor pagination is stabler under concurrent inserts but awkward for jump-to-page. *Suggested:* offset/limit with a hard `LIMIT` ceiling, and restrict `ORDER BY` to the existing `*DatabaseColumns` enums so the sort field can never come from raw request text — this is a home server with one library, and the stability problem cursors solve isn't real here.
- **Do the RPC-style route names stay now that the prefix is in place?** The router's own comment block states the rule of thumb (`GET` read / `POST` create / `PUT`-`PATCH` update / `DELETE` delete, [api_routes.rs:38-44](../../src/routes/api_routes.rs#L38)), but the paths beneath it are verbs — `/get_libraries`, `/delete_library/{id}`, `/setup_db` — and `/get_cover/{kind}/{id}` implies a `kind` discriminator no handler consumes. *Suggested:* leave the names alone for now but decide before F1 couples to them, since renaming paths later is the same two-codebase change the `/api/v1` prefix was chosen to avoid.
- **Bridge `log` into `tracing`, or standardise on `tracing`?** `main` installs `tracing_subscriber::fmt::init()` ([main.rs:9](../../src/main.rs#L9)) but no `log` → `tracing` bridge is configured, so all 24 `log::error!` calls in the codebase are dropped. This directly undercuts the "5xx details logged" half of the status-code decision: `DatabaseError::into_response` uses `tracing::error!` and is fine, while `RequestErrors::into_response` uses `log::error!` ([error_types.rs:211](../../src/error_types.rs#L211)) and would log nothing even if that branch were reachable. Options: (a) add the `tracing-log` bridge / enable `tracing`'s `log` feature and leave the call sites alone, (b) rewrite the 24 call sites to `tracing::error!` and drop the `log` dependency. *Suggested:* (b) for one logging front-end rather than two, but (a) as a one-line stopgap if the rewrite isn't worth doing right now.
- **Where does the first test actually run?** `Database::new()` hard-codes `./data/databases/app_data.sqlite` ([db.rs:26-63](../../src/database_related_scripts/db.rs#L26)) and `get_file_path()` ignores `self` ([models.rs:41-47](../../src/data_models/models.rs#L41)), so a test that constructs a `Database` writes to the real DB. Options: (a) make the DB path injectable, (b) test the traits directly against a `Connection::open_in_memory()` that `migrations::run` has been applied to. *Suggested:* (b) first — it needs no production change and is exactly the extract/insert/batch surface the roadmap wants covered; make the path injectable only when a handler-level integration test is wanted.

## Implementation notes

- **Two blockers sit in front of any work here.** First, the crate does not compile: five errors, all empty-bodied TOTP handlers declared `-> Response<Body>` at [api_caller.rs:617-625](../../src/routes/api_caller.rs#L617) — so `cargo test` cannot run until [04-two-factor-auth-totp.md](04-two-factor-auth-totp.md) either fills or removes them. Second, the axum 0.8 path syntax: replace `:id` with `{id}` and `:kind` with `{kind}` on the eight registrations listed above. The panic message axum emits is *"Path segments must not start with `:`. For capture groups, use `{capture}`."*
- **Copy `DatabaseError::into_response` as the pattern.** It is the one place in the codebase that gets the shape right: `match self` for the status, then branch on `status.is_server_error()` to decide whether the client sees `Display` text or a fixed generic string. Any new `IntoResponse` (for `AppErrors`, say) should be that same eight-line shape.
- **`setup_new_transaction` flattens the error you want to surface.** It logs the inner error but replaces it with `DatabaseError::OperationFailure` ([db.rs:400-403](../../src/database_related_scripts/db.rs#L400)), so a specific `AuthenticationError::EmailTaken` can never reach the client as a 409 or 400 no matter how good the `IntoResponse` is. Fixing status codes for transactional handlers means preserving the closure's own error out of that function first.
- **Sorting: reuse the column enums as the whitelist.** The codebase's SQL-safety convention is that values are always bound parameters while table and column names are only ever interpolated from trusted enums or consts. The `*DatabaseColumns` enums already implement `AsRef<str>` and are used exactly this way by `Update` ([db_update.rs:11-63](../../src/database_related_scripts/db_update.rs#L11)) and `Search` ([db_search.rs:12-95](../../src/database_related_scripts/db_search.rs#L12)) — so a sort parameter should be parsed into one of those enum variants and rejected if it doesn't match, never spliced in as a string. `LIMIT`/`OFFSET` are plain integers and can be bound as normal parameters.
- **Rust shape for the pagination parameters:** define a small `ListParams` struct with `Option<...>` fields deriving `Deserialize`, and take `Query<ListParams>` as a handler argument alongside `State` and `Path` — axum fills it from the query string, and `Option` means an absent parameter is `None` rather than an error. The SQL itself is built inside the `Extract` default methods ([extract.rs:33](../../src/database_related_scripts/extract.rs#L33)), so adding `ORDER BY`/`LIMIT` means either extending `extract_batch` or adding a sibling default method next to it rather than touching each impl.
- **Rust shape for the tests:** unit tests live in a `#[cfg(test)] mod tests { use super::*; ... }` block at the bottom of the same file, each function marked `#[test]`; async ones need `#[tokio::test]` instead. Multi-module tests that drive the app from outside go in a top-level `tests/` directory. For the DB layer the cheapest starting point needs no production change at all: `rusqlite::Connection::open_in_memory()`, then `migrations::run(&mut conn)` — which is idempotent and takes `&mut Connection` ([migrations.rs:26](../../src/database_related_scripts/migrations.rs#L26)) — then call `T::insert` / `T::extract` / `T::extract_batch` directly against that connection.
- **The first DB test will probably fail, and that's the point.** Three known column-name bugs are sitting in `FromRow` waiting to be found: `LibraryMetadata` reading `"name"` instead of `library_name` ([db_from_row.rs:71](../../src/database_related_scripts/db_from_row.rs#L71)), `"rocovery_id"` ([db_from_row.rs:111](../../src/database_related_scripts/db_from_row.rs#L111)), and `"last§"` ([db_from_row.rs:126](../../src/database_related_scripts/db_from_row.rs#L126)). A round-trip insert-then-extract test per type surfaces all three immediately.
- **Router state will have to grow.** `set_up_routes() -> Router<Arc<Database>>` means handlers can only reach the database; the secrets loaded and dropped at [main.rs:12](../../src/main.rs#L12) are already the first thing that doesn't fit. When something needs both, the idiomatic move is a single `AppState` struct holding `Arc<Database>` plus whatever else, used as the router's state type — worth doing once rather than twice.
- **EPUB cover validation is a real correctness check, not a formality.** The current implementation takes `epub.images.first()` — the first image in the resource list, *not* the manifest/OPF `cover` item ([cover_image_retriever.rs:119-141](../../src/scanner/cover_image_retriever.rs#L119)) — and derives the file extension from `media_type.split('/').nth(1)`, so `image/svg+xml` yields `svg+xml`. A test with a real EPUB is what turns "untested" into either "works" or a known bug.
