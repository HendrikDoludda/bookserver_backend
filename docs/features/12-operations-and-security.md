# Operations & Security

> The hardening, secrets handling, and deployment work that keeps a LAN + Tailscale home server honest — plus the deliberate decision about what *not* to build.

**Status:** 🟡 partial · **Phase:** 1 · **Tier:** Cross-cutting, mostly unscheduled — TLS and "user_id always from the session token" ride along with Backend Tier 1 · **Tags:** [BE] [FE]
**Depends on:** [03 Authentication, Users & Sessions](03-auth-users-and-sessions.md) (session-derived user ids, session revocation and in-app TLS all live in the auth step) · [04 Two-Factor Authentication (TOTP)](04-two-factor-auth-totp.md) (the signing key’s one concrete use is encrypting the TOTP secret at rest)
**Blocks:** Nothing
**Roadmap:** [Build order](../../ROADMAP.md#priority-order-build-sequence)

## Why

This is a personal home server, not a public SaaS, and the security work should be sized to that. The point of this document is to say exactly which hardening is mandatory regardless of the network model, which is low-urgency because of it, and which items are deliberately *excluded* as over-engineering — so effort goes to the handful of things that actually matter (session identity, secret handling, error bodies) instead of a generic checklist. It also carries the operational work that has no other home: deployment/packaging, file reconciliation, and `cargo audit`.

## Current state

- **No middleware whatsoever.** `grep -rn "layer(" src/` returns zero hits; the router at [api_routes.rs:45-70](../../src/routes/api_routes.rs#L45) has no CORS layer, no rate limiter, no body-size limit, no `TraceLayer`, and no `CookieManagerLayer`. Everything in this doc that would be a tower layer is not started.
- **TLS: nothing implemented.** [Cargo.toml](../../Cargo.toml) has no `axum-server` / `tls-rustls` dependency, and `start_server` binds a plain `TcpListener` ([api_routes.rs:20-36](../../src/routes/api_routes.rs#L20)). The roadmap's 🟡 marker reflects the *decision* being made, not code existing.
- **Signing key: generated, persisted, parsed, and thrown away — verified by grep.** `set_up_config_file` ([config.rs:20-45](../../src/config.rs#L20)) creates `secrets.toml` and `create_new_set_up_secrets` ([config.rs:47-59](../../src/config.rs#L47)) fills it with 32 random `SysRng` bytes, base64-encoded. [main.rs:12](../../src/main.rs#L12) binds it as `let secrets = ...` and immediately drops it — `start_server(db)` on the next line takes only the DB, and router state is `Arc<Database>` alone. A whole-tree grep for `token_signing_key|signing_key|Secrets|set_up_config_file` matches only `config.rs`, that one `main.rs` line, and the prose design comment at [auth.rs:543-566](../../src/routes/auth.rs#L543). **Nothing consumes it.** Session and refresh tokens use *unkeyed* BLAKE3 ([auth.rs:519-530](../../src/routes/auth.rs#L519)) and no value in the DB is encrypted. `chacha20-poly1305 = "0.2.1"` sits in [Cargo.toml:24](../../Cargo.toml#L24) and is never imported — the only mention of it anywhere in `src/` is a line of that same prose comment ([auth.rs:560](../../src/routes/auth.rs#L560)) — and `ApplicationSetUpErrors::KeyEncodingFailure` ([error_types.rs:320](../../src/error_types.rs#L320)) is never constructed.
- **File permissions: not set.** The TODO is live in the code — "*For the future the file should be marked as restricted so only the author is allowed to open the file not other users*" at [config.rs:34](../../src/config.rs#L34). `secrets.toml` is written with default permissions via `fs::write` + `fs::rename`; the SQLite file created by `Database::new` ([db.rs:26-63](../../src/database_related_scripts/db.rs#L26)) likewise.
- **Generic error bodies: half done.** `DatabaseError::into_response` ([error_types.rs:74-88](../../src/error_types.rs#L74)) already does the right thing — 5xx logs via `tracing::error!` and returns the literal `"Internal server error"`. But `create_internal_server_error_response` ([api_caller.rs:629-634](../../src/routes/api_caller.rs#L629)) interpolates the raw error `Display` string straight into the 500 body, and every hand-rolled auth handler uses it (11 call sites); `scan_all_directories` ([api_caller.rs:311-313](../../src/routes/api_caller.rs#L311)) and `log_out` ([api_caller.rs:484-486](../../src/routes/api_caller.rs#L484)) leak the same way with the `format!` inline rather than through the helper. `RequestErrors::into_response` ([error_types.rs:203-218](../../src/error_types.rs#L203)) has a sanitising `is_server_error()` branch that is **dead code** — none of its three variants map to 5xx.
- **Path traversal: unprotected, but not yet reachable.** `request_file` ([api_caller.rs:279-288](../../src/routes/api_caller.rs#L279)) hands `metadata.file_path` straight to `ServeFile` with no check that it sits inside a configured book dir. The intended fix is already a file-header TODO: "*Check if the file paths that get served are inside the database table for scannable files or the cover images folder*" ([api_caller.rs:4](../../src/routes/api_caller.rs#L4)). Safe today only because the path comes from a DB row keyed by id, never from the request.
- **Session revocation: a handler exists, is unrouted, and its SQL is wrong.** `log_out` ([api_caller.rs:480-489](../../src/routes/api_caller.rs#L480)) calls `remove_entry(DatabaseTypes::Session, session.0.session_id)`, which emits `DELETE FROM session WHERE id = ?1` — wrong table name (`DatabaseTypes::Session` maps to the singular `"session"` at [models.rs:37](../../src/data_models/models.rs#L37) while the migration creates `sessions`) *and* wrong primary key (`session_id`, not `id`). `POST /api/v1/log_out` is still wired to the `ping_server` placeholder ([api_routes.rs:61](../../src/routes/api_routes.rs#L61)). There is no list-sessions or revoke-one endpoint.
- **Invalidate-on-password-change: comment-only stub.** `password_changed()` ([auth.rs:412-414](../../src/routes/auth.rs#L412)) is an empty body containing only `//remove all active sessions and refresh tokens.` and has no callers; `change_password` ([api_caller.rs:509-531](../../src/routes/api_caller.rs#L509)) does not touch sessions.
- **Active-session data already exists.** The `sessions` table stores `device_id`, `device_name`, `platform`, `created_at`, and `last_used_at` ([0001_initial_schema.sql:80-94](../../migrations/0001_initial_schema.sql#L80)), so the "active sessions" listing has its columns already.
- **Audit log: nothing, and the plumbing has a gap.** No security-event logging exists. Two logging front-ends are in play: `tracing_subscriber::fmt::init()` at [main.rs:9](../../src/main.rs#L9) plus 24 `log::error!` call sites across `src/` — with no `tracing-log` bridge in [Cargo.toml](../../Cargo.toml), those `log::*` records are currently dropped.
- **`user_id`-from-the-token is already the shape, just not enforced.** The extractor exists but is named `AuthSession`, not `AuthUser` ([api_caller.rs:80-95](../../src/routes/api_caller.rs#L80)), and it yields the whole `Sessions` row. `change_password` ([api_caller.rs:518](../../src/routes/api_caller.rs#L518)), `change_username` ([api_caller.rs:543](../../src/routes/api_caller.rs#L543)) and `change_email` ([api_caller.rs:568](../../src/routes/api_caller.rs#L568)) already read `session.0.user_id` rather than a body field. None of them are routed, so nothing enforces the rule yet.
- **`cargo audit`: not in the workflow.** No `.github/`, no `audit.toml`, no `deny.toml` in the repo.
- **File reconciliation: absent.** `create_book_entry` skips a file whose `file_path` is already in the DB ([folder_scanner.rs:119-122](../../src/scanner/folder_scanner.rs#L119)) and nothing ever prunes or flags rows whose file was moved or deleted.
- **Deployment / packaging: nothing.** No Dockerfile, no bundling. Relevant constraint: `get_file_path()` ignores `self` and always returns `./data/databases/app_data.sqlite` ([models.rs:41-47](../../src/data_models/models.rs#L41)), and `COVER_DIR = "./cover_images/"` ([cover_image_retriever.rs:13](../../src/scanner/cover_image_retriever.rs#L13)) — both relative to the process CWD.

**Roadmap drift:**
- "Generic error bodies to the client" is marked ⬜ but is genuinely 🟡 — the `DatabaseError` path already sanitises 5xx and logs the detail, and the roadmap already counted that half as done on its status-codes item ("5xx details logged, generic body to client"), now carried by [Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md) at 🟡 for the same kind of reason. What remains is the hand-rolled `create_internal_server_error_response` path.
- "Session revocation + active sessions management" is marked ⬜, but a `log_out` handler already exists — it is simply unrouted and its SQL targets a non-existent table/column. Code presence is ahead of the marker; working behaviour is not.
- "TLS / HTTPS" is marked 🟡, which reads as partially built. Nothing is built: there is no TLS dependency and no TLS code. The 🟡 tracks the decision, not progress.
- The signing-key item's 🟡 is accurate in that the key *is* generated — but grep confirms zero consumers, and it is not even reachable from a handler, so wiring it would first require router state to grow beyond `Arc<Database>`.

## Decisions

- **Threat model: LAN-only, remote access via Tailscale.** LAN-only for now; remote access via **Tailscale** (WireGuard mesh VPN), *not* public port-forwarding. Tailscale keeps the server off the public internet and already encrypts traffic in transit, so for the LAN + Tailscale case the network-facing hardening in this doc is **low-urgency**.
- **App-level auth is mandatory regardless of the network model.** Tailscale controls *which devices* can reach the box; auth controls *who you are* and what you can do once in. That separation is needed for multi-user separation, so [auth](03-auth-users-and-sessions.md) is required no matter how good the network perimeter is.
- **The *(public only)* marker.** Items tagged *(public only)* become urgent **only** if the server is ever exposed directly to the open internet. They stay on the list, deliberately de-prioritised, rather than being deleted.
- **TLS is part of the auth step, in-app, and no longer "public only".** Moved out of this section into [auth](03-auth-users-and-sessions.md) and done in-app via `axum-server` (`tls-rustls`), because it protects the login credential + TOTP handshake even on the LAN and enables browser secure-context features. A reverse proxy (**Caddy**) remains a valid alternative if in-app certificate renewal ever annoys. Cert-source options live in the auth doc — not duplicated here.
- **Sessions are opaque DB-backed tokens, not signed JWTs.** A random value is generated, its BLAKE3 hash is stored, and revocation is a row delete. This is the premise the whole exclusion list below rests on.
- **Deliberately excluded — JWT-specific hardening.** Signing access tokens, `jti` blocklists, and signing-key rotation are excluded *because* sessions are opaque DB tokens: revocation is a row delete and there is no signature to manage. The `previous_token_signing_key` rotation scaffolding in `secrets.toml` only matters **once the key is actually used** for something.
- **Deliberately excluded — over-engineering for this threat model.** The application-level hardening list came out of a security-checklist review, scoped to a LAN + Tailscale, few-user, admin-registration home server. On that scoping the following are out: **suspicious-login / anomaly detection**, **account lockout** (itself a DoS vector), **hardware-backed key storage**, and **blanket encryption-at-rest**.
- **Signing key: decide its job or drop it.** `config.rs` generates a 256-bit key into `secrets.toml` but nothing uses it. Because sessions are opaque DB tokens, the key adds **nothing** to token storage — the tokens are already high-entropy. Its one concrete use here is **encrypting the TOTP secret at rest** (a [2FA](04-two-factor-auth-totp.md) open decision) via an AEAD (`chacha20poly1305` / `aes-gcm`). If nothing consumes it, **remove it rather than carry unused crypto.**
- **TOTP verify rate-limiting is the priority throttle, not login rate-limiting.** A 6-digit code is only 1,000,000 combinations, so it is brute-forceable even behind Tailscale — that throttle is real work, tracked in [2FA](04-two-factor-auth-totp.md). Ordinary login rate-limiting stays *(public only)*, since there is no anonymous attacker on the tailnet.
- **Error bodies: detail to the log, generic message to the client.** Handlers currently return `err.to_string()` in the response body, which can leak internal detail. Log the detail server-side; send the client only a status plus a generic message.
- **`user_id` always comes from the session token, never the request body.** This is *the single rule* that prevents one user acting as another. Get it right when the `AuthUser` extractor lands.
- **Audit log lives in `tracing`, not in a table.** Record failed logins, password changes, and session revocations as log events. **Never** log passwords, tokens, or the signing key.
- **CORS is configured only once a browser client exists.** No point configuring it before the web frontend or the [admin web view](06-admin-web-view.md) actually calls the API.
- **File reconciliation is a data-integrity item, not a security one.** It lives in this section for convenience, but it is about the DB matching the disk.

## Open questions

- **Keep the signing key or delete it?** Keeping it means wiring `Arc<Secrets>` into router state (or introducing an `AppState`) and using it as an AEAD key for the TOTP secret; deleting it means removing `set_up_config_file`, the `secrets.toml` handling, and the unused `chacha20-poly1305` dependency, and dropping the 0600 task for that file. Carrying it unused is the one option with no upside. *Suggested:* resolve it together with the [2FA](04-two-factor-auth-totp.md) plaintext-vs-encrypted-at-rest decision — if that lands on encrypted, keep the key and wire it; if it lands on plaintext, delete the key, the rotation fields, and the crypto dependency in the same change.
- **Which logging front-end carries the audit log?** The decision says "via `tracing`", but the codebase currently uses `log::error!` in 24 places while only `tracing_subscriber` is initialised, so those records go nowhere. Options: write audit events with `tracing::info!`/`warn!` directly (no bridge needed, but the existing `log::error!` calls stay invisible); or add the `tracing-log` bridge so both front-ends land in one stream; or migrate the `log::*` calls to `tracing`. *Suggested:* write audit events with `tracing` macros and add the bridge, so the existing error logs become visible at the same time — migrating the 24 `log::error!` call sites can wait.
- **Fix logout's SQL as part of session revocation, or as part of the wider `WHERE id` problem?** `remove_entry` hard-codes `WHERE id`, and `DatabaseTypes` has no correct name for `sessions` — the same class of bug affects `totp`, `recovery_codes`, `email_verification`, and `reset_password_requests`. *Suggested:* treat it as one fix in [Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md) (teach the DB layer each table's real PK column) rather than special-casing sessions, since revocation, TOTP disable, and password reset all need it.
- **Where do the SQLite DB and cover images live once packaged?** Both paths are hard-coded relative to the process CWD, which conflicts with a Docker persistent volume and with a `.dmg`/`.exe` install. Options: make both configurable by env var (consistent with the existing config style); or derive them from `directories::ProjectDirs`, which is already a dependency and is what `secrets.toml` uses. *Suggested:* `ProjectDirs` as the default with an env-var override — it makes the macOS/Windows packaging targets work without extra flags, and the Docker case just points the override at the mounted volume.
- **Does path containment validate against the scannable-directories table or the configured dirs?** The code TODO assumes the table, which does not exist yet ([Library & Directory Management](01-library-and-directory-management.md), Tier 2). *Suggested:* implement the containment check against `get_books_dirs()` + `cover_images/` now so the helper exists and is tested, then re-point it at the table when that lands — the check itself is the same canonicalise-and-compare either way.

- ⬜ **Derive `user_id` from the session token, never from the request body** — the single rule that prevents acting as another user; get it right when the `AuthUser` extractor lands ([Authentication, Users & Sessions](03-auth-users-and-sessions.md)) **[BE]**

## Done when

- [ ] `ls -l` on `secrets.toml` and the SQLite file both show `-rw-------`, and a second local user account cannot read either.
- [ ] A 500 response from any auth handler carries a generic body (no error `Display` text, no table or column names), while the specific error appears in the server log.
- [ ] `POST /api/v1/log_out` deletes the caller's session row, and a subsequent request with that same session token gets 401; a request to the sessions-list endpoint returns the caller's remaining sessions with device/platform, and revoking one by id makes that token 401 too.
- [ ] Changing a password invalidates every other session for that user — a token issued before the change gets 401 afterwards.
- [ ] A failed login, a password change, and a session revocation each produce exactly one log line, and grepping the log for the submitted password, any session token, or the signing key finds nothing.
- [ ] `GET /api/v1/book/:id` refuses to serve a file whose stored `file_path` resolves outside the configured book dirs or `cover_images/`, returning 404 rather than the file.

## Implementation notes

- **Reading the signing key needs router state to grow first.** [main.rs:12](../../src/main.rs#L12) already produces `Arc<Secrets>` but `start_server(db)` takes only the DB, and `Router` state is `Arc<Database>`. The Rust shape is to introduce an `AppState { db: Arc<Database>, secrets: Arc<Secrets> }`, make it the router state type, and have handlers extract `State<AppState>` — Axum requires every handler on that router to agree on one state type, so this is a single mechanical change across all handlers, not something you can do for one endpoint. `Secrets` is also currently a **private** struct returned from a `pub fn` ([config.rs:14](../../src/config.rs#L14)); it must become `pub` (and its fields accessible) before another module can use the key.
- **0600 on Unix is `std::os::unix::fs::PermissionsExt`.** Either `fs::set_permissions(path, fs::Permissions::from_mode(0o600))` after writing, or better, create the file with `std::fs::OpenOptions::new().mode(0o600).write(true).create_new(true)` so the file is never briefly world-readable. Both need `#[cfg(unix)]`, since `from_mode` does not exist on Windows — on Windows the equivalent is ACL work and is fair to skip for now. Note the existing write goes to `secrets.toml.tmp` then renames ([config.rs:35-38](../../src/config.rs#L35)); set the mode on the **temp** file before the rename so there is no window where the real path is readable.
- **CORS and rate limiting are tower layers on the router.** `tower-http` is already a dependency with `features = ["full"]`, so `tower_http::cors::CorsLayer` needs no new crate — apply it with `.layer(...)` on the router in `set_up_routes`. Rate limiting would need a new crate (`tower_governor` is the usual choice); it is *(public only)*, so it does not need to be added yet.
- **Path containment: canonicalise both sides, then compare.** `Path::canonicalize()` resolves `..` and symlinks and errors if the path does not exist; the check is `canonical_file.starts_with(canonical_root)`. Comparing *before* canonicalising is the classic mistake — `/books/../etc/passwd` passes a naive string prefix check. `starts_with` on `Path` compares whole components, so it will not accidentally match `/books-secret` against a `/books` root the way a string prefix would.
- **Password-hash upgrade-on-login uses the parsed PHC string.** `validate_submitted_password` ([auth.rs:303-318](../../src/routes/auth.rs#L303)) already parses `user.password_hash` into a `PasswordHash`. Its `params` are readable from that value, so the upgrade check is: after a successful `verify_password`, compare the stored params against `Argon2::default()`'s, and if they differ, re-hash the plaintext (still in scope at that point) and write the new hash. Marked low priority in the roadmap.
- **Audit logging is structured fields, not string formatting.** `tracing::warn!(user_id, event = "login_failed", "authentication failed")` keeps the event greppable. The discipline that matters is the exclusion list: never interpolate a password, a token (plaintext *or* hashed), or the signing key into a log line — which also means not `Debug`-printing `Sessions`, `TOTP`, `EmailConfig`, or `UserMetadata`, all of which currently derive `Serialize`/`Debug` over secret-bearing fields.
- **`cargo audit` is a separate binary:** `cargo install cargo-audit`, then `cargo audit` against `Cargo.lock`. It is not part of `cargo` itself, and it needs no code changes — just a documented step (and later a CI job; there is no `.github/` yet).
- **File reconciliation needs the scanner to look the other way.** Today the scan walks the disk and asks "is this file in the DB?". Reconciliation is the reverse query — walk the `books` rows and ask "does this `file_path` still exist?" — so it is a separate pass, not a tweak to `create_book_entry`. `file_hash` and `last_modified` are already stored ([0001_initial_schema.sql:2-20](../../migrations/0001_initial_schema.sql#L2)), so a moved file can be *matched by hash* and updated rather than deleted and re-inserted. Decide prune-vs-flag before writing it; flagging is safer for a library you care about.
- **Packaging gotcha — pdfium.** Cover extraction uses `Pdfium::default()`, which needs the dynamic pdfium library resolvable at runtime, and there is already a TODO about bundling it so a Mac run does not need a manual symlink ([cover_image_retriever.rs:75-76](../../src/scanner/cover_image_retriever.rs#L75)). Any `.dmg` / `.exe` / Docker image has to ship that library, so treat it as part of the packaging task rather than a surprise at the end.
- **Warning from the roadmap, restated:** do not add the excluded items opportunistically. Account lockout in particular is *itself a DoS vector* on a few-user server — one attacker who knows a username can lock the owner out of their own library.
