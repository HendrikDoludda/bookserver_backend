## Why

These came up while writing the roadmap and did not belong anywhere yet. **Nothing in this doc is scheduled or agreed** — the original framing was "pick what's interesting, ignore the rest." The list keeps them from being lost while making clear they are unaccepted, and it has already earned its keep: two entries were promoted out of it into real phases (incremental scanning → Phase 1, OPDS → Phase 2). Everything still listed here is a decision waiting to be made, not work waiting to be done.

## Current state

Nothing in the code implements any of the five ideas. What exists is the surrounding machinery each one would attach to:

- **File watching (idea 1)** — no watcher of any kind. Scanning is manual and full: `scan_all_folders` ([folder_scanner.rs:34](../../src/scanner/folder_scanner.rs#L34)) walks every configured dir on every run, and `create_book_entry` skips a file only when its `file_path` is already a row ([folder_scanner.rs:119](../../src/scanner/folder_scanner.rs#L119)) — with the live TODO `//check for modification as well and then update` on the next line. The `notify` crate is **not** a dependency ([Cargo.toml](../../Cargo.toml)).
- **Thumbnails (idea 2)** — cover extraction is live per format via `get_cover_image` ([cover_image_retriever.rs:16](../../src/scanner/cover_image_retriever.rs#L16)), writing one full-size file per book to `./cover_images/<hash>.<ext>` ([cover_image_retriever.rs:195](../../src/scanner/cover_image_retriever.rs#L195)). The only resize anywhere is the PDF render target width of 1000 ([cover_image_retriever.rs:89](../../src/scanner/cover_image_retriever.rs#L89)); no re-encoding to a uniform format, no second smaller file. `image = "0.25.10"` is already a dependency ([Cargo.toml:37](../../Cargo.toml#L37)). Serving covers at all is still a **route skeleton wired to the placeholder handler** — `GET /get_cover/:kind/:id` → `ping_server` ([api_routes.rs:63](../../src/routes/api_routes.rs#L63)), and no handler consumes the `:kind` segment.
- **Per-library permissions (idea 3)** — no permission model. `users` has a single `is_admin BOOLEAN` ([0001_initial_schema.sql:57](../../migrations/0001_initial_schema.sql#L57)) and no `role` column; the `AdminSession` extractor that checks it exists ([api_caller.rs:60](../../src/routes/api_caller.rs#L60)) but is **wired to nothing**. There is no user↔library table — the only junction today is `library_elements` (library↔series, composite PK, no `id`) ([0001_initial_schema.sql:32](../../migrations/0001_initial_schema.sql#L32)).
- **Format-aware reading position (idea 4)** — no read state exists at all: no table, no column, no struct, no per-user anything. `books` carries `page_count` and `page_number` ([0001_initial_schema.sql:12](../../migrations/0001_initial_schema.sql#L12), [:15](../../migrations/0001_initial_schema.sql#L15)), but neither is usable: `page_number` is filled from the filename regex ([folder_scanner.rs:151](../../src/scanner/folder_scanner.rs#L151)), not from a reading position, and `page_count` is fed from a field `get_file_metadata` always sets to `None` ([folder_scanner.rs:146](../../src/scanner/folder_scanner.rs#L146), [:191](../../src/scanner/folder_scanner.rs#L191)), so it is NULL for every row. `BookFormat` ([models.rs:83](../../src/data_models/models.rs#L83)) already distinguishes `Pdf | Epub | Cbz | ImageComic | None`. Both reading-progress routes are **placeholder-handler skeletons**: `PATCH|GET /reading_progress/:id` → `ping_server` ([api_routes.rs:57](../../src/routes/api_routes.rs#L57)).
- **DB backup/export (idea 5)** — no backup endpoint, no export, no `VACUUM`, nothing. The SQLite file path is hardcoded in two places: `Database::new` ([db.rs:27](../../src/database_related_scripts/db.rs#L27)) and `DatabaseTypes::get_file_path()` ([models.rs:41](../../src/data_models/models.rs#L41)), which ignores `self` and always returns `./data/databases/app_data.sqlite`. Connections are opened with `journal_mode = WAL` ([db.rs:37](../../src/database_related_scripts/db.rs#L37)).

Roadmap drift: idea 1 is no longer purely a proposal. "Watch scannable directories for changes — filesystem notifications on file add/remove, debounced, then re-scan only the modified folders" is already a committed ⬜ task in [Library & Directory Management](01-library-and-directory-management.md) (the doc that inherited the pre-split roadmap's Phase 1 §1), carrying the same "builds on incremental scanning; `notify` crate is the usual approach" note — so it was effectively promoted like incremental scanning and OPDS, but this ideas list was never updated to say so. It currently exists in both places.

## Decisions

- **These are proposals, not commitments.** The section was written as "these came up while writing the list — pick what's interesting, ignore the rest." Nothing here has a tier, a phase or a status marker in the build sequence, and nothing should be started off this doc alone. Recording that explicitly is the point: an idea list that reads like a plan quietly grows the plan.
- **Promotion out of the list is how an idea becomes work.** Already exercised twice — **incremental scanning → Phase 1** (now [Library & Directory Management](01-library-and-directory-management.md)) and **OPDS → Phase 2** (now [Interop & Client Apps](23-interop-and-clients.md)). An accepted idea moves into the owning feature doc's task list and stops being an idea; that keeps a single place per feature and stops the backlog doubling as a shadow roadmap.
- **Per-library permissions is gated on roles existing.** The idea's own wording is "once roles exist" — so it cannot be evaluated, let alone built, before [Authentication, Users & Sessions](03-auth-users-and-sessions.md) lands a role model. Today there is only `is_admin`.
- **The format difference in reading position is a design constraint regardless of acceptance.** The idea's own reasoning: "page number" works for PDF/CBZ, but EPUB needs a locator/CFI because reflowable text has no fixed pages — so it is "worth designing the read-state schema with this difference in mind from the start." Even if the idea is never expanded into features, the schema in [Reading & Read State](02-reading-and-read-state.md) should not be written as a bare integer page.

## Open questions

- **Is idea 1 (file watching) accepted or not?** It is simultaneously a proposal here and a ⬜ task in Phase 1 §1. Options: (a) treat it as promoted, delete it from this list, and let [Library & Directory Management](01-library-and-directory-management.md) own it — clean, but locks in a dependency chain (watching builds on incremental scanning, which is itself not started); (b) treat the §1 task as the aspiration and leave it here as unaccepted — keeps it honest but leaves the same item in two places. **Suggested:** (a) — the §1 entry is more specific (debounced, re-scan only modified folders) than this one, so the roadmap has already made the call; drop the duplicate here once §1's version is confirmed.
- **If thumbnails (idea 2) are accepted, pre-generate or resize on demand?** Pre-generating at scan time costs disk and one more write per book but makes serving a static file read; resizing per request costs CPU on every grid load with no extra disk. **Suggested:** pre-generate alongside the existing cover write in `cover_image_retriever.rs` — the scan already touches every file once and already writes a cover, so it is the cheapest place to add a second output.
- **Does per-library permissions (idea 3) overlap [Sensitive Content Controls](10-sensitive-content-controls.md) enough to be one mechanism?** §9's "optional per-user visibility" and this idea's "kids' library" are close to the same feature from two directions. Options: one generic per-user/per-library visibility table that sensitive-content flags also consult, or two independent mechanisms (an `is_sensitive` flag plus a separate ACL). **Suggested:** decide this *before* either is built — one visibility check is easier to reason about than two that can disagree, but only if both features genuinely want the same granularity. *Update:* there are now **three** claimants on the same user↔library table, not two — [Download Permissions](24-download-permissions.md) (Phase 2) wants a per-user "may keep the original file" right on the same axis. That strengthens the case for one access model with a column per capability, settled when the role model lands.
- **What locator shape does idea 4 imply for the read-state schema?** Options: a single `TEXT` locator column plus a discriminator (one shape for every format, parsing pushed to the reader), or separate nullable columns (`page INTEGER`, `locator TEXT`) with the format deciding which is meaningful. **Suggested:** the `TEXT` locator plus discriminator — `BookFormat` already exists to be that discriminator, and it avoids a schema change the first time a new format needs a position that is neither a page nor a CFI.
- **What exactly does the backup endpoint (idea 5) back up, and who may call it?** Options: DB only (small, and covers are re-derivable by re-scanning the source files), or DB plus `./cover_images/` (bigger, but restores instantly). Access: admin-only, or unauthenticated like the existing mutating endpoints. **Suggested:** DB only, admin-gated behind the (currently unwired) `AdminSession` extractor — the catalog is the irreplaceable part, and an unauthenticated endpoint that hands out the whole user table is strictly worse than no endpoint.
- **Do any of the five get accepted at all in this pass?** They compete with Tier 0–4 work that is already sequenced and gated. **Suggested:** accept none of them now except deciding idea 4's schema question (which is free, and expensive to retrofit), and revisit the rest when the tier that owns each is actually in front of you.

## Implementation notes

**Nothing here is buildable today regardless of acceptance:** the crate does not compile, and once it does, `set_up_routes` still panics at startup on the axum 0.8 path syntax. Both blockers are owned by [Cross-Cutting Backend Polish](07-cross-cutting-backend-polish.md) and must clear before any idea here can be prototyped.

- **Idea 1 (`notify`)** — a new dependency; it is not in `Cargo.toml`. The non-obvious Rust shape: `notify` delivers events on its own OS-watcher thread via a callback, not as an async stream, so the usual pattern is to send each event into a `tokio::sync::mpsc` channel from that callback and do the debouncing in a single async task that reads the channel (collect events, wait for a quiet period, then re-scan the affected folders). The roadmap's own note stands: this **builds on incremental scanning** — without the `file_hash` + `last_modified` comparison, a "re-scan the modified folder" event still does a full folder pass, and `create_book_entry` will skip every existing row rather than update it.
- **Idea 2 (thumbnails)** — no new crate needed: `image` is already a dependency and already used in `cover_image_retriever.rs`. `image::DynamicImage::thumbnail(w, h)` is the fit-preserving resize. Two gotchas in the existing code to work around: the CBZ path has no `final_path.exists()` short-circuit and so re-extracts on every scan (the other three formats do short-circuit), and `get_cover_output_path` builds the filename with `Path::with_extension` on the hash while the caller passes `file_hash.clone().unwrap_or_default()` ([folder_scanner.rs:135](../../src/scanner/folder_scanner.rs#L135)), so on a hashing failure the extension lands on the *directory* name and the cover is written to `./cover_images.jpg` — one file beside the cover folder, shared by every such book. A thumbnail variant inherits both. *Suggestion, not a decision:* the `:kind` segment in `GET /get_cover/:kind/:id` is consumed by no handler today, so it is a natural place to select full-size vs thumbnail without adding a route.
- **Idea 3 (per-library permissions)** — the fitting shape is a second junction table alongside `library_elements`: composite PK `(user_id, library_id)`, **no `id` column**, therefore it does **not** implement `Extract` (whose default `WHERE id = ?1` / `row.get(0)`-as-id contract cannot hold) and instead gets dedicated `Database` methods, exactly as `library_elements` does. Enforcement wants the same rule the auth work already commits to: derive `user_id` from the session, never from the request body. `AdminSession` already exists and needs wiring regardless.
- **Idea 4 (read position)** — nothing to reuse; `books.page_number` is scanner-parsed filename data and must not be repurposed as read state. If the locator is stored as `TEXT`, the Rust shape that keeps callers honest is an enum (`Page(i64)` / `Locator(String)`) converted at the DB boundary in `FromRow`, rather than an `Option<i64>` plus an `Option<String>` that callers have to remember to check in the right order.
- **Idea 5 (backup)** — **warning: with `journal_mode = WAL`, copying the `.sqlite` file alone is not a valid backup** (recent commits may live only in the `-wal` file). Use `VACUUM INTO 'path'` executed on a pooled connection — one `conn.execute` call, no new dependency — or rusqlite's online backup API, which needs the `backup` feature enabled on the `rusqlite` dependency. Note also that the DB path is hardcoded twice ([db.rs:27](../../src/database_related_scripts/db.rs#L27) and [models.rs:41](../../src/data_models/models.rs#L41)); a backup endpoint is a good reason to make it one value. Related standing item from [Operations & Security](12-operations-and-security.md): the SQLite file should be `0600` — a backup endpoint that streams the DB to any caller undoes that.
