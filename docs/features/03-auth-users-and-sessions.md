## Why

Auth is the single foundation that everything per-user waits on: read state, "continue reading", plan-to-read, uploads, sensitive-content controls and the admin UI all need to know *who* is asking. Tailscale controls *which devices* reach the box; auth controls *who you are* and what you can do once in — which is what makes multi-user separation possible at all. It is also the biggest single piece in the roadmap, so getting the session model and the `user_id`-from-token rule right here saves reworking every later feature. TLS was deliberately folded into this step because login carries a password (and later a TOTP code) that should not cross even the LAN in cleartext.

## Decisions

- **Opaque DB-backed sessions, not JWTs** — sessions are a random value stored hashed in a `sessions` table row; revocation is a row delete. Rationale: logout and revocation are trivial (delete the row), and there is no signature to manage, no `jti` blocklist, no signing-key rotation. This is why the JWT-specific hardening items are explicitly excluded from the security list.
- **Argon2 for passwords** — no hand-rolled crypto. Implemented as `Argon2::default()` (Argon2id, random salt per hash, PHC string stored in `users.password_hash`).
- **BLAKE3 for tokens** — session and refresh tokens are 32 random bytes hex-encoded, and only the BLAKE3 hash is stored. Rationale: the tokens are already high-entropy, so a fast hash is enough; a DB leak does not hand over usable tokens. (Currently **unkeyed** — see the signing-key question below.)
- **Access + refresh token split** — `session_token_hashed` short-lived (15 minutes) + `refresh_token_hashed` long-lived (30 days), each with its own `*_valid_until` column. The roadmap's intent was a sliding expiry "refreshed on use"; the implementation issues a **whole new pair** on refresh (rotation), which is stricter and also gives reuse detection a place to live.
- **Half-authenticated sessions via `authentication_completed`** — a session row starts with `authentication_completed = !totp_enabled`. `AuthSession` requires it `true`; `AuthTOTPLoginSession` requires it `false`. Rationale: the TOTP step gets a real, expiring, device-bound session to carry state instead of an ad-hoc pending-login store.
- **Device-bound sessions** — `device_id`, `device_name` and `platform` are stored on the session row, which is what makes an "active sessions / revoke this device" screen possible later.
- **Email verification on sign-up** — an 8-char code, Argon2-hashed into `email_verification`, 15-minute expiry, one live row per user (`user_id` is the PK, so re-issuing overwrites rather than appends). Verifying returns a real session, so the user is logged in straight after verifying.
- **`user_id` comes from the session, never the request body** — `change_password` / `change_username` / `change_email` all take `session.0.user_id`. This is the single rule that prevents acting as another user; keep it when the remaining endpoints are wired.
- **Generic credential errors** — user lookup by email-or-username maps "not found" to `IncorrectCredentials` ([auth.rs:211](../../src/routes/auth.rs#L211)) so the response cannot be used to enumerate accounts. The password-reset flow is meant to do the same: "If email is valid an email has been sent", the same message whether or not the address exists ([auth.rs:330](../../src/routes/auth.rs#L330)).
- **HTTPS / TLS in-app, as part of the auth step (DECIDED)** — serve over TLS with `axum-server` (`tls-rustls`): `RustlsConfig::from_pem_file(cert, key)` + `bind_rustls`. Rationale: login sends the password **and** the TOTP code, so encrypt the transport even on LAN (defense-in-depth) and unlock browser secure-context features. This is why TLS was pulled out of "public only" and into Tier 1.
- **Cert source: `tailscale cert`** — real and trusted for the tailnet, and it fits the network model. Long-lived self-signed is the simplest alternative but produces trust warnings. **Not** Let's Encrypt unless the server is ever public.
- **Renewal is the only ongoing piece** — `axum-server` supports hot cert reload (`RustlsConfig::reload_from_pem_file`), so renewal needs no restart. Serving itself is trivial. A reverse proxy (Caddy) stays a valid alternative if in-app renewal ever becomes annoying.

## Open questions

- **Open self-service sign-up vs admin-only registration — the headline divergence.** The roadmap decided *admin-only* registration: the first admin is bootstrapped (e.g. from env on first run) and **only admins create further users**, which is exactly *why* the roadmap wanted an admin/member role at all. The code implements *open* sign-up (`sign_up` needs no session at all) plus email verification plus first-user-becomes-admin. Options: (a) keep open sign-up + email verification — no bootstrap step, but anyone who can reach the box can create an account, which on a Tailscale-only LAN is a small but real exposure and makes `email_verified` the only gate; (b) go back to admin-only — `sign_up` becomes `AdminSession`-gated, the email-verification code becomes an invite/welcome mail instead of a gate, and a startup bootstrap path is needed; (c) hybrid — keep the code's flow but add a config switch (`REGISTRATION_OPEN`) defaulting to closed. *Suggested:* (c) — it preserves the working code path and honours the decision by default; if only one is picked, follow the roadmap and gate `sign_up` behind `AdminSession`, since a home server with a handful of known users has no need for self-service.
- **How the first admin is created.** Roadmap: bootstrap from env on first run. Code: `validate_new_user` grants admin to whoever signs up while no admin row exists — and then `UserMetadata::insert` drops the flag entirely, so today *nobody* can be admin. Options: env-bootstrapped admin at startup (deterministic, survives an empty-but-not-fresh DB, needs one more config surface); fix the insert so first-user-becomes-admin actually works (less config, but "no admin exists yet" is a weaker condition than "no users exist" and races with an open sign-up). *Suggested:* fix `UserMetadata::insert` regardless (the dropped flag is a plain bug), then add the env bootstrap as the authoritative path and keep first-user-becomes-admin only if sign-up ends up admin-only.
- **Where the tokens travel: `Authorization` header, cookie, or JSON body?** Three different answers exist right now — the roadmap says `Authorization` header, the extractors read cookies, and `create_auth_response` returns the tokens in a JSON body. Options: cookies (`HttpOnly`, `Secure`, `SameSite=Lax`) — best for the browser clients (main frontend + admin UI), needs `CookieManagerLayer` and a CSRF story for state-changing requests; `Authorization: Bearer` — best for the Flutter app and for WebDAV-adjacent clients, no CSRF surface, but the token lives in client storage; both — extractor tries the header, falls back to the cookie. *Suggested:* do **both**, cookie-first for browsers and header for the app, and have `create_auth_response` set the cookies *in addition* to returning the JSON — that is the smallest change that makes the existing extractors work.
- **`role` column vs `is_admin` boolean.** The roadmap task says add `role` to `users`; the schema and `UserMetadata` use `is_admin: bool`. Options: keep the boolean (simplest, matches `AdminSession` as written, fine for admin/member); switch to a `role` TEXT column (room for a third role later — e.g. the kids'-library idea in the ideas backlog — at the cost of a migration and touching every `is_admin` site). *Suggested:* keep `is_admin` for v1 and mark the roadmap's `role` task as satisfied by it; revisit only if per-library permissions land.
- **Is email verification required to log in?** `log_in` never checks `email_verified` ([auth.rs:281](../../src/routes/auth.rs#L281)), so an unverified account can sign in normally. Options: enforce it (verification actually gates access, but locks people out whenever SMTP is misconfigured); leave it advisory (a flag for the admin UI only). *Suggested:* enforce it, but only once the SMTP fallback question below is resolved — otherwise a missing SMTP config becomes a total lockout.
- **The no-SMTP auto-verify fallback.** When `get_email_config()` returns `None`, `sign_up` treats `EmailSetUpNotFound` as licence to call `auto_verify_account` ([api_caller.rs:393](../../src/routes/api_caller.rs#L393)), which self-verifies the account with device fields hard-coded to `"Unknown"` and hands back real session + refresh tokens. Convenient for solo dev; as a shipping default it means "no SMTP configured" silently disables email verification. Options: keep it but require an explicit opt-in flag (e.g. `ALLOW_AUTO_VERIFY=1`, dev only); drop it and fail sign-up with a clear "server email is not configured" error; keep it only while no admin exists (bootstrap-only). *Suggested:* gate it behind an explicit dev flag — the current behaviour is a security default set by the absence of config, which is the wrong way round.
- **Refresh-token reuse detection.** Rotation is implemented but nothing notices a refresh token being presented twice, and `update_existing_session` has a self-documented race ([auth.rs:444-447](../../src/routes/auth.rs#L444)) that the maintainer already suggests fixing by turning the blind update into a search-then-update on the old token value. Options: leave it (small user count, Tailscale-only); conditional update (`WHERE refresh_token_hashed = <old>`) so a replay affects 0 rows and can be detected; full "reuse ⇒ kill the whole session family". *Suggested:* the conditional update — it is a one-line SQL change that closes the race and gives replay detection for free.
- **`device_id` uniqueness is global, not per user.** `sessions.device_id` is `UNIQUE` on its own ([0001_initial_schema.sql:83](../../migrations/0001_initial_schema.sql#L83)) and `create_new_session` never replaces an existing row, so a second login from the same device — or two users on one device — hits the unique constraint. It is also declared `BINARY(16)` in SQL but `String` in Rust ([models.rs:428](../../src/data_models/models.rs#L428)), and the value is client-supplied. Options: `UNIQUE(user_id, device_id)` plus delete-then-insert on re-login; drop the constraint and allow many sessions per device; server-generated device ids (the unused `uuid` crate is already a dependency). *Suggested:* `UNIQUE(user_id, device_id)` with an upsert on login, and treat the client-supplied id as a hint only.
- **Changing an email address without re-verification.** `change_email` writes the new address straight to `users.email` and leaves `email_verified` untouched ([api_caller.rs:558](../../src/routes/api_caller.rs#L558)), so a verified account keeps its verified flag on an unverified address. Options: set `email_verified = false` and re-issue a verification code; verify the *new* address first and only then swap. *Suggested:* verify first, swap second — otherwise password-reset mail can be redirected by anyone holding a session.
- **Shape of per-user settings.** Nothing exists yet: no table and no extra columns on `users`. It has to hold at least the user's locale, because the i18n plan assumes the backend can read it to localize emails. Options: columns on `users` (simplest, one row per user, a migration per new setting); a `user_settings` table keyed by `user_id` (one row per user, wide); a key/value `user_settings(user_id, key, value)` junction (schema-free, but no typing and no defaults in SQL). *Suggested:* a typed `user_settings` table keyed `user_id PRIMARY KEY` — same shape as `totp` / `email_verification`, and it keeps `users` about identity.
- **Does the signing key have a job here?** [config.rs:47](../../src/config.rs#L47) generates a 256-bit key into `secrets.toml` and nothing consumes it; the design notes at the end of the auth module describe using it for **keyed** BLAKE3 of refresh tokens, encrypting sensitive config values and signing internal data ([auth.rs:543-566](../../src/routes/auth.rs#L543)). Because sessions are opaque high-entropy tokens, keying the hash adds nothing to token storage. Its one concrete use in this project is encrypting the TOTP secret at rest. *Suggested:* leave tokens on unkeyed BLAKE3 and decide the key's fate in [Operations & Security](12-operations-and-security.md) / [TOTP](04-two-factor-auth-totp.md) — if nothing consumes it, remove it rather than carry unused crypto.
- **Duplicate function names across the two auth files.** `log_out`, `reset_password` and `request_reset_password*` exist twice — once as a comment-only stub in [auth.rs](../../src/routes/auth.rs), once as a real handler in [api_caller.rs](../../src/routes/api_caller.rs). *Suggested:* delete the dead stubs and keep their comment plans as the checklist for the real handlers (`password_changed`'s "remove all active sessions" note is the one worth keeping as a real function).

## Implementation notes

- **Crates already present:** `argon2 = "0.6.0"`, `blake3`, `rand = "0.10.2"` (`SysRng` is the OS CSPRNG — it replaced `OsRng` in rand 0.10, and `try_fill_bytes` comes from the `TryRng` trait), `hex`, `tower-cookies = "0.11.0"`, `uuid` (declared, unused). **Missing for the TLS task:** `axum-server` with the `tls-rustls` feature.
- **Two logging front-ends are in use.** [main.rs:9](../../src/main.rs#L9) initialises `tracing_subscriber`, but the auth code logs via `log::error!`. Without a `tracing-log` bridge those `log::*` records are currently dropped — so the "log the detail server-side, send a generic body" pattern is only half working. Pick one front-end before relying on the audit trail.
- **Rust shape — the extractor.** An Axum extractor is a `struct` plus `impl FromRequestParts<Arc<Database>> for MyType`, where `from_request_parts` returns `Result<Self, Self::Rejection>` and the rejection type implements `IntoResponse`. That is exactly what `AuthSession` does, and layering (`AdminSession` calling `AuthSession::from_request_parts` first, then checking `is_admin`) is the idiomatic way to build role gates — keep that composition instead of duplicating cookie parsing.
- **Rust shape — handler argument order.** Axum only lets the **last** handler argument consume the request body. So `Json<T>` (or any body extractor) must come last, and `State`, `Path` and custom `FromRequestParts` extractors must come before it. `sign_in`, `verify_email`, `change_*`, `reset_password` and `request_reset_password_link` all violate this today, which is why they cannot be passed to `.route()` as written.
- **Rust shape — router state.** Router state is `Arc<Database>` ([api_routes.rs:21](../../src/routes/api_routes.rs#L21)), which is why the signing key loaded at [main.rs:12](../../src/main.rs#L12) is unreachable from handlers. If anything ever needs the key (or SMTP config, or the TLS paths), introduce a single `AppState { db, secrets, … }` struct and make that the state — every `State<Arc<Database>>` extractor then becomes `State<AppState>`.
- **Transactions.** `Database::setup_new_transaction(|conn| …)` takes a closure returning `Result<T, AppErrors>` and gives every `*_with_connection` associated function a shared connection, so a multi-step flow (validate → create user → issue code) commits or rolls back as one unit. The gotcha: it currently **discards** the closure's specific error and returns `DatabaseError::OperationFailure`, logging the real cause. Auth needs the specific error to survive, otherwise every failure is a 500 with a useless message.
- **Error mapping.** `AppErrors` has no `IntoResponse`, so each auth handler hand-maps. The current handlers use `create_internal_server_error_response`, which **interpolates the raw error string into the 500 body** — the opposite of what `DatabaseError::into_response` does. Fix that when wiring: log the detail, send status + generic message. Note also that `RequestErrors::RequestFailed` maps to **400**, not 500, despite three inline `// 500` comments saying otherwise ([api_caller.rs:126](../../src/routes/api_caller.rs#L126), [:180](../../src/routes/api_caller.rs#L180), [:231](../../src/routes/api_caller.rs#L231)) — which means genuine server faults inside `authorized` currently surface as 400, and the `is_server_error()` branch in that `IntoResponse` impl is dead code.
- **Email sending is inline and synchronous** in the request path, so an unreachable SMTP host stalls the HTTP response. The SMTP config is also re-read from env on every send. Both are tracked in [Email & Notifications](14-email-and-notifications.md).
- **`UserMetadata` derives `Serialize` including `password_hash`** ([models.rs:257](../../src/data_models/models.rs#L257)), and `Sessions` serializes both hashed tokens. Never return either struct directly from a handler — build a response DTO.
- ⚠️ **Restrict file permissions to owner-only (`0600`)** on `secrets.toml` (the TODO is already at [config.rs:34](../../src/config.rs#L34)) and on the SQLite DB file — this is tracked in [Operations & Security](12-operations-and-security.md) but is worth doing while touching config here.
- ⚠️ **Login rate-limiting** stays *(public only)* for now — there is no anonymous attacker on the tailnet. The priority throttle is the **TOTP verify** rate-limit, because a 6-digit code is only 1,000,000 combos; see [TOTP](04-two-factor-auth-totp.md).
- *Suggestion, not scope:* the maintainer is new to Rust and the roadmap already plans to learn Rust testing together (§6). The `Extract` / `Insert` / `Search` round-trip for `Sessions` and `UserMetadata` would be a good first test target — every one of the column-name bugs listed above (`"last§"`, `"user_id"` vs `id`, `WHERE id` on `sessions`) is exactly what a single insert-then-read test would have caught.
