# Sensitive Content Controls

> An admin-only `is_sensitive` flag on libraries and series that changes how those items behave — starting with never sending their titles to third-party metadata APIs.

**Status:** ⬜ not started · **Phase:** 1 · **Tier:** Backend Tier 4 (fourth item, last in the tier) · **Tags:** [DB] [BE] [FE]
**Depends on:** [03 Authentication, Users & Sessions](03-auth-users-and-sessions.md) (the toggle is admin-only, so it needs roles) · [09 Metadata Enrichment (Online Sources)](09-metadata-enrichment.md) (the "sensitive items skip online lookups" rule needs provider dispatch to exist)
**Blocks:** Nothing
**Roadmap:** [Build order](../../ROADMAP.md#priority-order-build-sequence)

## Why

Admins can mark a library or series as sensitive, which changes its behaviour. The concrete, non-negotiable part is privacy: a metadata lookup sends the item's title to an external service (§8's provider list — Google Books / Open Library for books, AniList / MangaDex / MangaUpdates for manga, Comic Vine / Metron for comics), so anything marked sensitive must be excluded from those lookups rather than trusted to a UI-side filter. Everything beyond that — hiding items from default views, blurring covers, per-user visibility, a PIN — is a deliberate "pick later" list; the roadmap records the candidates without saying why they are deferred (the likely reason: the useful part, the flag plus the lookup skip, is small, while the rest is policy that is easier to decide once it is actually being used). The roadmap puts it last in Tier 4 (uploads → admin UI → theming → sensitive content) and names it among the things waiting on auth, because the toggle needs an admin/member distinction to check and admin screens to sit on.

## Decisions

- **The flag lives on library and series, not on individual books.** The roadmap scopes `is_sensitive` to those two tables, so a single book cannot be marked on its own — the smallest markable unit is a series. The roadmap gives no rationale for that scoping; the reading that fits is that sensitivity is a property of a collection you curate, so the flag goes where curation already happens.
- **Toggling is admin-only.** Marking something sensitive is a privileged operation, which is why this feature is listed as depending on roles from the auth step — it cannot be built before there is an admin/member distinction to check.
- **Sensitive items skip *all* online metadata lookups.** Rationale, stated in the roadmap: don't leak titles to third-party APIs — privacy. This is the coupling point with metadata enrichment; the skip is the whole reason the flag is worth having on its own.
- **The extra protections are deliberately not chosen yet.** The candidate list is recorded ("pick later"): hidden from default views / explicit opt-in, optional per-user visibility, blurred covers, optional PIN or re-auth to open. The roadmap states only that the choice is deferred, not why — the reading that fits is that the flag plus the lookup skip is the part with a clear payoff, while the rest is policy that is cheaper to decide when there is something to look at.
- **Build order: last in Tier 4.** The Tier 4 sequence is uploads → admin UI → theming → sensitive content, and the Tier 1 dependency note lists sensitive content among the things waiting on auth. Rationale: it needs roles (Tier 1) and the admin screens (Tier 4) before the toggle has anywhere to live.
- **The toggle is an API endpoint, not UI behaviour.** Per the project's guiding principle — everything must be changeable from both the frontend and the backend web view, achieved by making every mutation an HTTP endpoint that both UIs merely call. So "admin-only toggle on the library & series screens" is one backend endpoint consumed by two clients, never logic duplicated in either UI.

## Open questions

- **Does the filtering happen in the backend or the frontend?** The DB-layer TODO ([db.rs:19-20](../../src/database_related_scripts/db.rs#L19)) says both are valid and leans backend. Backend: sensitive titles never leave the process, but every list query and the (future) search path needs the predicate. Frontend: nothing to change server-side, but the titles are already on the wire and any client can see them. *Suggested:* backend, at the SQL level in `get_all_libraries` / `get_series_entries_in_library` — a client-side filter is cosmetic, not a control.
- **Does sensitivity inherit from library → series (→ books)?** The roadmap puts the flag on both tables without saying how they compose. Independent flags: simplest, but marking a library sensitive leaves its series individually unmarked and therefore reachable by a direct series request. Inherited: an item is sensitive if its library *or* its series is, which matches the intuition "I marked this shelf sensitive" but needs a join on every read. *Suggested:* effective sensitivity = library OR series, computed in the backend, so marking the library is enough.
- **Which extra protections actually get built, and in what order?** The candidates and their costs: *hidden from default views / explicit opt-in* — cheap, one query predicate plus a request flag; *optional per-user visibility* — needs a new user×library (or user×series) table, i.e. a second `library_elements`-style junction, and overlaps with the "per-library permissions" idea in the [Ideas Backlog](90-ideas-backlog.md); *blurred covers* — frontend-only if covers still ship, backend work if they must not; *optional PIN or re-auth to open* — reuses the session machinery from auth but adds a second credential to manage and recover. *Suggested:* build only hidden-from-default-views plus explicit opt-in with the first pass, and leave the other three unbuilt until something concretely needs them.
- **Can an admin manually override the lookup skip for one item?** The roadmap says "skip *all* online metadata lookups", which reads absolute. A manual bypass would be convenient when an admin wants a description for a sensitive series, but it reintroduces exactly the leak the rule exists to prevent. *Suggested:* honour it as absolute with no bypass — a sensitive item gets manually entered metadata only (which the metadata feature already provides via manual edit/override of any field).
- **Should sensitivity affect cover extraction, or only cover display?** Covers are extracted at scan time into `cover_images/` regardless, and serving them is still a placeholder route (`GET /get_cover/:kind/:id` → `ping_server`, [api_routes.rs:63](../../src/routes/api_routes.rs#L63)). If "blurred covers" is picked, blurring in the client is trivial; refusing to extract is not, and would break the roadmap's "series & library covers default to the first entry's image" plan. *Suggested:* keep extracting, treat blurring as a display concern.

## Done when

- [ ] A migration adds `is_sensitive` to both `library` and `series` with a `NOT NULL DEFAULT FALSE`, and every pre-existing row reads back as not sensitive.
- [ ] The toggle request with a valid non-admin session returns **403**; the same request with an admin session flips the flag, and a following `GET` on that library/series reflects the new value.
- [ ] Exactly one route writes `is_sensitive`, and both the frontend and the backend admin web view call it — grepping for `IsSensitive` finds no second write path that only one UI can reach.
- [ ] Running a metadata lookup over a library marked sensitive produces **zero** outbound HTTP requests for that library's series (observable against a stub provider or in the request log).
- [ ] With a library marked sensitive and its series not (and the reverse), `get_libraries`, `get_series_from_library/:id` and `get_series_children/:id` all report the same sensitivity answer for that item — no endpoint disagrees with another.

## Implementation notes

- **The schema change.** `ALTER TABLE library ADD COLUMN is_sensitive BOOLEAN NOT NULL DEFAULT FALSE;` (same for `series`) is legal in SQLite precisely because a default is supplied, and existing rows take the default. Registration is a new numbered `.sql` file plus a new `Migration` entry in the `MIGRATIONS` array ([migrations.rs:16-20](../../src/database_related_scripts/migrations.rs#L16)) — each pending migration runs in its own transaction, so a multi-statement file is all-or-nothing. Note your standing early-dev practice of editing `0001_initial_schema.sql` in place and wiping the DB instead; that stays fine until the frontend is reading real data, after which this needs to be a real `0002_*.sql`.
- **Adding a column to a model touches five places, and only two of them are compile-checked.** For each of `LibraryMetadata` / `BookSeriesMetadata` you need: the struct field ([models.rs:292](../../src/data_models/models.rs#L292), [models.rs:226](../../src/data_models/models.rs#L226)), a new variant plus its `AsRef<str>` arm in the column enum ([models.rs:300-316](../../src/data_models/models.rs#L300), [models.rs:235-253](../../src/data_models/models.rs#L235)), the column added to `Extract::COLUMNS` ([extract.rs:85-88](../../src/database_related_scripts/extract.rs#L85), [extract.rs:79-83](../../src/database_related_scripts/extract.rs#L79)), a `row.get("is_sensitive")?` in `FromRow` ([db_from_row.rs:66-77](../../src/database_related_scripts/db_from_row.rs#L66), [db_from_row.rs:54-64](../../src/database_related_scripts/db_from_row.rs#L54)), and the column plus its bound param in `Insert` ([insert.rs:86-107](../../src/database_related_scripts/insert.rs#L86), [insert.rs:61-84](../../src/database_related_scripts/insert.rs#L61)). The struct field and the enum match are the two the compiler will shout about; `COLUMNS`, `from_row` and the `INSERT` string are plain strings and positional params, so getting them wrong fails at **runtime**, not at `cargo check`. Change all five together.
- **Gotcha already sitting in that code path:** `LibraryMetadata::from_row` reads `row.get("name")` ([db_from_row.rs:71](../../src/database_related_scripts/db_from_row.rs#L71)) while `Extract::COLUMNS` selects `library_name` ([extract.rs:87](../../src/database_related_scripts/extract.rs#L87)) — so reading a library row fails today and `GET /api/v1/get_libraries` cannot succeed. Don't debug your new flag against that endpoint until that mismatch is fixed, or you'll chase the wrong bug.
- **The toggle needs no new DB plumbing.** `Update` is already implemented for both `LibraryMetadata` and `BookSeriesMetadata` ([db_update.rs:70-78](../../src/database_related_scripts/db_update.rs#L70)), so the handler body is essentially `db.update_value::<LibraryMetadata>(LibraryDatabaseColumns::IsSensitive, &true, id)` ([db.rs:81-95](../../src/database_related_scripts/db.rs#L81)). `Update::update`'s hard-coded `WHERE id = ?2` ([db_update.rs:22-26](../../src/database_related_scripts/db_update.rs#L22)) genuinely matches `library.id` and `series.id`, so unlike the auth tables (whose PKs are `session_id` / `user_id` / `recovery_id`) this path works as written. Booleans round-trip as SQLite `INTEGER` 0/1 with `rusqlite`, exactly like `users.email_verified` / `users.is_admin` do in `UserMetadata::from_row` ([db_from_row.rs:79-94](../../src/database_related_scripts/db_from_row.rs#L79)).
- **Admin gating shape.** Put `AdminSession` first in the handler's argument list — as a `FromRequestParts` extractor it runs before the body is consumed, and its `Rejection` already produces the 403, so the handler body never sees a non-admin. Two blockers in the auth layer must be cleared first, both tracked with auth: no `CookieManagerLayer` is installed on the router anywhere, so every cookie-reading extractor currently fails with 400; and `Sessions::from_row` reads a column literally named `"last§"` ([db_from_row.rs:126](../../src/database_related_scripts/db_from_row.rs#L126)), so every session read errors out. Until both are fixed, `AdminSession` cannot succeed for anyone.
- **Where to put the lookup skip (suggestion).** Gate it once, in the provider dispatch that routes by library type, rather than inside each adapter — a single check at the top means a newly added provider cannot forget it, whereas a per-adapter check is one omission away from a leak.
- **Both models derive `Serialize`** ([models.rs:292](../../src/data_models/models.rs#L292), [models.rs:226](../../src/data_models/models.rs#L226)), so the moment the field exists it appears in every JSON list response automatically. That is convenient for the frontend, but it also means an unauthenticated caller can read `is_sensitive` off the live, ungated list endpoints before any filtering lands — worth knowing, not necessarily worth blocking on.
- **If PIN / re-auth is eventually picked**, it reuses the existing session machinery rather than any new crypto — `hash_string_securely` ([auth.rs:532-541](../../src/routes/auth.rs#L532), private to `auth.rs` today, so it would need `pub` or a wrapper) and the `sessions` table ([0001_initial_schema.sql:80-94](../../migrations/0001_initial_schema.sql#L80)) are already there.
